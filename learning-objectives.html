학습 목표 정리 — 세션별 "무엇을 학습/습득해야 하는가"

2일·16시간 과정의 세션별 학습 목표·산출물·핵심 용어를 한 장에 모았습니다. 강의 내용을 검토하고 개선안을 도출하기 위한 자료입니다(원본 세션 설명: docs 포털, 실행 코드: labs/, 용어: 중급과정 용어사전).

15 세션 (Day1 S0~S6 · Day2 S0~S7)학습 목표 = 수강생이 할 수 있어야 하는 것산출물 = 학습의 증거핵심 용어 = 용어사전 ID

결과물 검증 기준 — 페르소나 · 바라는 점 · 전달 내용 · 목적 (확정 기준)

이 섹션의 역할(확정): 아래 네 가지는 강의(결과물)가 잘 만들어졌는지를 검증하는 기준점입니다 — 모든 세션·산출물·리허설·계측이 이 목표에 비춰 판정됩니다. 확정 사항: 주 대상 = P-A(기능팀 실무 개발자), 아래 4개 검증 목표 = 수료 판정 기준(P-B·P-C는 보조 대상). 조정이 필요하면 이 섹션만 고치면 하위 검증이 함께 갱신됩니다.

1 · 수업을 듣는 사람의 페르소나 (누가 배우는가)

P-A · 기능팀 실무 개발자 주 대상

매일 Copilot을 쓰지만 대체로 "그냥 만들어줘" 수준. 반복 구현·리팩토링·테스트에 시간을 쓰고, AI 산출물을 어디까지 믿어야 하는지 불안하다.

P-B · 팀 리드 / PL

팀에 Copilot을 안전하게 도입하고 싶다. 자율성을 어디까지 허용할지, 사람 승인·리뷰·비용/보안 경계를 기준으로 잡고 싶다.

P-C · 품질 / 플랫폼 담당

반복 업무와 검증을 재사용 자산(Skill/Agent)·로컬 게이트·정책으로 표준화해 팀 전체에 퍼뜨리고 싶다.

준비도 축(리허설용): 준비형(본인 기능 지참·환경 GREEN) · 표준형(초안·환경 YELLOW) · 폴백형(기능 미지참·환경 RED → 샘플 폴백). 페르소나는 역할×준비도로 교차합니다.

전달의 기준: "안다"가 아니라 "손에 쥐는 산출물"로 전달되어야 합니다. 개념 설명만 있고 증거(산출물)가 없는 세션은 검증 실패 신호입니다.

4 · 수업을 듣고 이루어야 하는 목적 (검증 목표)

수료 시점에 다음이 증거물로 존재하면 결과물(강의)은 목적을 달성한 것으로 검증합니다.

  • ▢ 본인 기능 1건으로 end-to-end 체인 완성: 기능 스펙 → 토큰절약 프롬프트 → AC/Plan/Test Matrix → Feature Spec Pack v1 → 로컬 게이트 → spec.md·테스트·리뷰패킷 → Custom Skill/Agent → 공유 1페이지.
  • ▢ 검증 가능성: 모든 변경이 test + policy-check + rollback note로 되돌릴 수 있고 설명 가능한 상태(Go/No-Go 통과).
  • ▢ 재사용성: 산출물이 일회성이 아니라 다음 주 바로 쓸 수 있는 Skill/Agent·게이트로 남음.
  • ▢ 현업 이전성: PL handoff 1페이지 + 현업 적용 액션 3개로 팀에 전파 가능(D+7 클리닉으로 연결).
페르소나별 달성 상태: P-A = "내 기능을 검증 가능하게 구현하고 되돌릴 수 있다" · P-B = "팀에 적용할 통제·승인 기준을 정했다" · P-C = "재사용 Skill/게이트 1개를 자산으로 만들었다". 이 세 문장이 모두 참이면 강의는 목적을 달성한 것입니다.

이 과정의 약속 — 수료 시 갖춰야 할 5가지 역량

1 · 좋은 입력토큰·프롬프트·Plan으로 좋은 입력을 만든다
2 · 안전한 실행하네스·Agent Teams·Fleet/Loop로 에이전트를 통제한다
3 · 검증 가능한 변경SDD·로컬 게이트로 검증 가능한 변경을 만든다
4 · 나만의 솔루션Custom Skill/Agent로 재사용 솔루션을 완성한다
5 · 경험 공유라이트닝 토크·PL handoff로 팀에 공유한다
읽는 법: 각 세션의 학습 목표는 "수강생이 끝나면 할 수 있어야 하는 것"이고, 산출물은 그 학습이 일어났음을 보여주는 증거물입니다. 둘이 1:1로 맞물리는지를 보면 학습 설계의 빈틈이 보입니다.

전체 역량 체크리스트 — 수료 시 "할 수 있어야 하는 것"

세션 학습 목표를 5개 역량 축으로 합친 최종 도달 상태입니다. 강의가 이 항목들을 실제로 달성시키는지 점검용으로 쓰세요.

1 · 좋은 입력 Day1

  • 범위를 좁혀(파일·#file·로그 제한) 토큰을 줄여 같은 결과를 낸다
  • 가드레일(금지 작업·민감정보 경계)을 프롬프트에 명시한다
  • 기능 스펙을 비식별화한다
  • R/C/T/C/V/O 6요소로 프롬프트를 구조화한다
  • User Story·AC·Business Process로 요구사항을 검증 가능하게 정제한다
  • 동작 불변을 보장한 리팩토링을 지시한다
  • Context Manifest로 볼 파일을 좁힌다
  • Plan Mode로 계획-실행을 분리하고 Test Matrix·rollback note를 만든다

2 · 안전한 실행 Day2

  • 하네스 개념(자연어 제약→실행 가능한 검증)을 설명한다
  • Copilot CLI 권한·로그(allow/deny-tool·log-dir)를 제어하고 로그를 해석한다
  • wrapper·policy-check로 로컬 검증 게이트를 만든다
  • Agent Teams 역할을 분리하고 기능팀에 매핑한다
  • Fleet 설계표·Loop Canvas로 모델·도구·중단 조건·게이트를 정의한다
  • 모델 라우팅 원칙(프롬프트 모델명 ≠ 보장)을 적용한다
  • 내 반복 업무를 하네스 워크플로로 분해한다

3 · 검증 가능한 변경 Day2

  • spec.md로 요구사항을 정형화한다
  • test-first(실패 테스트 먼저)로 최소 구현한다
  • evidence bundle을 만든다
  • rollback note·no-cloud attestation 포함 local review packet을 제출한다

4 · 나만의 솔루션 Day2

  • Custom Skill을 목적·입력·절차·금지·출력 구조로 작성한다
  • Custom Agent와 Fleet 운영 기준(모델·도구·중단)을 정한다

5 · 경험 공유 Day2

  • 라이트닝 토크로 전체 연결을 5분에 설명한다
  • 현업 적용 액션 3개와 PL handoff 1페이지를 만든다
