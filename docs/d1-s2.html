실습 1 — Before/After 프롬프트 (PT-05)

Before
면세 처리도 좀 넣어줘. 알아서 잘 고쳐줘.
After (R/C/T/C/V/O)
[역할] 너는 우리 기능팀의 결제 모듈 담당 개발자다.
[맥락] 고객 스펙(비식별): VAT 10%, 면세 품목 제외. 레거시 calcVat() 존재.
[작업] 면세 분기 추가 + 음수 입력 가드.
[제약] 외부 라이브러리 추가 금지. 기존 시그니처 유지.
[검증] 면세=0, 일반=10%, 음수=오류 케이스의 유닛테스트 포함.
[출력] 변경 diff 요약 → 코드 → 테스트 순서로.
"After가 토큰이 더 많은데, S1의 '토큰 절약'과 모순 아닌가?" — 단발 프롬프트만 보면 After가 더 깁니다. 하지만 절약의 기준은 '한 번의 프롬프트 길이'가 아니라 '작업 완료까지의 총 토큰'입니다.
  • S1(토큰 최적화) = 잡음을 뺀다 — 전체 레포·긴 로그 같은 불필요한 컨텍스트.
  • S2(구조화 프롬프트) = 신호를 넣는다 — 역할·제약·AC. 재작업을 막는 투자입니다.
  • 모호한 Before("알아서 잘 고쳐줘")는 엉뚱한 수정·되돌리기·재프롬프트로 턴이 쌓여, 입력+출력 토큰이 오히려 더 커집니다(2026-06-01~ 토큰 과금은 입력·출력을 모두 계산).
즉 잡음↓(S1) + 신호↑(S2) = 총 토큰↓. 두 세션은 충돌이 아니라 같은 목표의 양면입니다.

AC는 검증 가능해야: 모든 AC는 자동 테스트 또는 정책 체크로 확인 가능해야 합니다. "빠르다·직관적이다" 같은 느낌 기준은 AC가 아니라 non-goal로 분리하세요.

ActivityWatch 목표 힌트 · S2 User Story·AC

ActivityWatch의 event·bucket 개념처럼 “시간 구간의 활동을 모아 요약한다”는 방향을 참고하되, 실습 계약은 더 작은 { app, start, end } 모델입니다.

  • User Story 질문: 사용자는 세션 결과를 보고 어떤 결정을 하나요? 한 문장으로 사용자·기능·가치를 연결하세요.
  • 고정 계약 확인: FEATURE-SPEC.md와 src/activity.js의 TODO를 읽고 유효 event 필터, 시작 시각 정렬, 겹침 시 end 확장, ms 출력 규칙을 기록합니다. 이는 선택할 새 AC가 아니라 구현이 지켜야 할 기존 계약입니다.
  • 정상·경계 AC 질문: test/activity.test.js의 skip 테스트 이름과 합성 fixture를 보고, 임계값을 넘는 경우와 정확히 같은 경우의 기대 세션 수·count를 직접 계산해 적으세요.
  • 예외 AC 질문: baseline 테스트 이름에서 무효 event 또는 collector 실패 계약 하나를 골라 기존 기대값과 연결하세요. 새 예외 동작을 만들지 않습니다.
  • 증거 범위: Day2 필수 sessionize 증거는 기존 skip 2개를 켜는 것입니다. 추가 checkpoint 테스트를 요구사항처럼 늘리지 않습니다.

개념 주의: ActivityWatch의 AFK watcher가 기록하는 afk/not-afk 상태와, 이번 실습이 계산하는 이벤트 사이 유휴 간격은 같은 데이터가 아닙니다. 명시적 AFK 입력은 stretch 또는 non-goal로 남기세요.

참조 심화 — SMART AC · BDD 브래킷

SMART AC — 검증 가능한 조건의 5가지 기준

AC가 "잘 동작한다"에 머물면 모델도 사람도 완료를 판정할 수 없습니다. SMART는 AC를 측정 가능한 문장으로 만드는 체크리스트입니다. 특히 마지막 T는 "무엇으로 확인하나" — 즉 측정 source(테스트/명령)를 함께 적는다는 뜻입니다.

SMART 기준 · 질문 · 결제(VAT) 예
기준질문예
Specific · 구체적무엇이, 어떤 조건에서?"면세 품목"이라는 입력 조건을 명시
Measurable · 측정가능숫자/불리언으로 판정되나?VAT = 0 (정확한 기대값)
Achievable · 달성가능이번 slice로 가능한가?calcVat() 한 함수 범위
Relevant · 관련성기능 목표에 닿나?세금 정확도 목표에 직결
Testable · 테스트가능무엇으로 확인하나?(source)tax.test.js의 "AC2 면세=0"
✗ 모호한 AC: "면세 처리가 잘 된다." — 무엇이 '잘'인지, 무엇으로 확인하는지가 없습니다.
✓ SMART AC: "면세 품목을 입력하면 VAT는 0을 반환한다 — npm test의 AC2 면세 품목은 VAT 0으로 확인."

BDD 브래킷 — Given·When·Then으로 열고, 증거로 닫는다

한 작업 단위를 시작할 때 기대를 Given-When-Then으로 열고, 끝날 때 같은 문장에 증거(테스트 통과·커밋)를 붙여 닫습니다. 시작과 끝의 기준이 같아 "완료"가 흔들리지 않습니다.

① 열기 — 작업 전, 기대 정의
Given  면세 품목과 금액이 주어지고
When   calcVat(금액, { 면세: true }) 를 호출하면
Then   VAT 는 0 을 반환한다.
② 닫기 — 작업 후, 같은 문장 + 증거
Given 면세 품목 … When calcVat … Then VAT = 0   ✅
증거:
- npm test → "AC2 면세 품목은 VAT 0" pass
- commit abc1234 (tax.js: 면세 분기 추가)
왜 브래킷인가: 열기만 있으면 "했다"는 선언에 그치고, 닫기(증거)가 있어야 검증 가능한 변경이 됩니다. 이 열기/닫기 한 쌍은 Day2·S4 test-first(실패 테스트 → 통과)와 리뷰 패킷(증거 번들)으로 그대로 이어집니다.

실습에서 기대하는 바와 결과 예시

기대하는 바

  • User Story를 정상·예외·경계 AC로 바꾼다.
  • 각 AC가 사람이 실행할 테스트 또는 관찰 결과와 연결되게 한다.
  • Role·Context·Task·Constraint·Verification·Output을 빠짐없이 작성한다.

결과 예시

정상: gap > idleGapMs → 새 세션
예외: start >= end → 이벤트 제외
경계: gap == idleGapMs → 같은 세션
검증: 각 규칙을 독립 테스트 이름으로 연결
예시 해석: “잘 묶인다” 같은 표현 대신 입력 조건과 관찰할 결과가 한 문장에 있어야 합니다. 세 AC의 세부 문구는 달라도 정상·예외·경계가 모두 존재해야 합니다.
