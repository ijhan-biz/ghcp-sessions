실습 1 — Before/After 프롬프트 (PT-05)

Before
면세 처리도 좀 넣어줘. 알아서 잘 고쳐줘.
After (R/C/T/C/V/O)
[역할] 너는 우리 기능팀의 결제 모듈 담당 개발자다.
[맥락] 고객 스펙(비식별): VAT 10%, 면세 품목 제외. 레거시 calcVat() 존재.
[작업] 면세 분기 추가 + 음수 입력 가드.
[제약] 외부 라이브러리 추가 금지. 기존 시그니처 유지.
[검증] 면세=0, 일반=10%, 음수=오류 케이스의 유닛테스트 포함.
[출력] 변경 diff 요약 → 코드 → 테스트 순서로.
"After가 토큰이 더 많은데, S1의 '토큰 절약'과 모순 아닌가?" — 단발 프롬프트만 보면 After가 더 깁니다. 하지만 절약의 기준은 '한 번의 프롬프트 길이'가 아니라 '작업 완료까지의 총 토큰'입니다.
  • S1(토큰 최적화) = 잡음을 뺀다 — 전체 레포·긴 로그 같은 불필요한 컨텍스트.
  • S2(구조화 프롬프트) = 신호를 넣는다 — 역할·제약·AC. 재작업을 막는 투자입니다.
  • 모호한 Before("알아서 잘 고쳐줘")는 엉뚱한 수정·되돌리기·재프롬프트로 턴이 쌓여, 입력+출력 토큰이 오히려 더 커집니다(2026-06-01~ 토큰 과금은 입력·출력을 모두 계산).
즉 잡음↓(S1) + 신호↑(S2) = 총 토큰↓. 두 세션은 충돌이 아니라 같은 목표의 양면입니다.

실습 2 — 요구사항 정제 (User Story · BP · AC)

User Story
As a [사용자/시스템 역할],
I want [원하는 기능],
So that [업무 가치/품질 효과].
Business Process (SD-09)
[Event] 사용자가 금액을 입력한다.
[Task] 입력 유효성을 검사한다.
[Gateway] 음수 또는 면세인가?
  - 음수: 오류 반환
  - 면세: VAT 0
  - 일반: VAT 10%
[Task] 결과를 반환한다.
Acceptance Criteria (SD-03) — 정상·예외·경계로 분리
AC별 검증 방법 · source
AC검증 방법측정 source
음수 금액 입력 시 오류 반환unit testnpm test
면세 품목은 VAT 0unit testtax.test.ts
public API 시그니처 불변lint/checkernpm run lint
AC는 검증 가능해야: 모든 AC는 자동 테스트 또는 정책 체크로 확인 가능해야 합니다. "빠르다·직관적이다" 같은 느낌 기준은 AC가 아니라 non-goal로 분리하세요.
여기서 만든 AC는 Day1·S4의 Test Matrix(SD-05)와 Day2·S4~S5의 test-first(SD-06) 구현으로 그대로 이어집니다.

참조 심화 — SMART AC · BDD 브래킷

SMART + 측정 source: AC는 "잘 동작한다" 같은 모호한 문장이 아니라 측정 가능한 조건 + 측정 source(어느 테스트/명령으로 확인하는가)를 함께 적습니다.
BDD 브래킷: 한 단계를 Given-When-Then 문장으로 열고, 끝나면 같은 문장 + 증거 링크로 닫습니다. 시작과 끝을 같은 기준으로 묶어 "완료"를 못박습니다.

체크포인트 & 산출물

산출물: 본인이 작성한 프롬프트 3종(요구사항 정리·구현 후보·테스트 후보)과 AC 표.
  • 각 프롬프트에 6요소가 모두 있는가?
  • 각 AC가 테스트 또는 checker와 연결되는가?
  • Business Process에 예외 흐름(Gateway)이 있는가?
컷라인: 시간이 빠듯하면 User Story 1개 + AC 3개만 확실히. BP는 글머리 흐름으로 대체 가능.

흔한 실수 & 공유 포인트

  • 검증(V)을 빼먹음 → 모델이 "동작한다"고 선언하지만 근거가 없음. 항상 검증 요소를 넣습니다.
  • AC를 "잘 동작한다" 같은 모호한 문장으로 작성 → 정상/예외/경계 값으로 구체화합니다.
공유 포인트: "내 안티패턴 1개와 교정"을 기록하세요. 동료가 가장 빨리 배우는 형태가 Before/After입니다.
