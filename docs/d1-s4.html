미니강의 — 왜 계획을 먼저 받는가

에이전트는 한 번에 많은 것을 바꾸려 합니다. Plan Mode(CF-04)는 코드 작성 이전에 "무엇을, 어느 파일에서, 어떤 순서로, 무엇으로 검증하는가"를 합의합니다. 계획을 보고 잘못된 가정·과한 범위를 싸게 잡아낼 수 있습니다.

Plan Mode는 GitHub Copilot의 기본(내장) 기능입니다. 별도 확장이나 프롬프트 트릭이 아니라, VS Code Copilot Chat의 모드 선택기에서 Ask · Edit · Agent와 함께 제공되는 Plan 모드를 고르면 됩니다. Plan 모드는 코드를 바로 수정하지 않고 단계별 실행 계획을 먼저 생성하며, 사용자가 그 계획을 검토·편집·승인한 뒤 실행(예: Agent 모드로 핸드오프)합니다. 즉 이 세션에서 연습하는 "계획만 먼저" 흐름이 제품에 그대로 내장돼 있는 셈이며, Plan 모드가 없거나 제품 버전 차이로 보이지 않을 때는 아래 프롬프트로 같은 흐름을 만듭니다.
요구사항(AC)→계획(단계+stop point)→Test Matrix→risk/gate→단계별 실행
Plan Mode의 "단계별 실행 + stop point"는 Day2의 Loop(CF-06 Plan→Generate→Evaluate→Fix→Gate)로 자연스럽게 확장됩니다.

실습 — 계획부터 단계 실행까지

STEP 1 · 계획만 요청
[작업] 아래 기능 스펙(+AC)을 보고 구현 계획만 세워라. 코드 작성 금지.
[출력]
1. 변경 목표
2. 변경 파일 후보와 근거 (Context Manifest 참고)
3. 단계별 plan, 각 단계의 stop point
4. Test Matrix (AC ↔ 테스트)
5. risk tier와 Human Gate
6. rollback note 초안
[제약] 외부 패키지 추가 금지, public API 변경 금지, 실제 고객 데이터 금지.
AC → 테스트 변환 규칙: AC 원문을 테스트 이름으로 옮기고, 각 AC마다 정상·예외·경계 케이스를 뽑습니다. 예: "음수 금액은 오류" → 정상: 100원 OK · 예외: 음수 reject · 경계: 0원 처리 정의.
STEP 2 · 계획 검토·수정 → 2~3단계로 합의

계획이 4단계를 넘으면 범위가 큰 신호입니다. 2~4단계로 줄이고 각 단계에 stop point가 있는지 확인합니다.

정말 5단계+가 필요하면: 억지로 줄이지 말고 ① PL과 scope 재협상 ② Epic으로 보고 slice 1개만 오늘 처리 ③ 'High-risk'로 표시해 Approval Owner 사전 승인. 예: 데이터 마이그레이션 같은 큰 작업은 slice로 나눕니다.
중간 브레이크(2분): 100분 세션의 절반 지점입니다. STEP 2까지가 컷라인(계획 + Test Matrix) — 여기까지면 최소 통과입니다. 잠깐 스트레치 후 STEP 3(실행)으로 갑니다. 시간이 부족하면 STEP 3~4는 Day2로 이월합니다.
STEP 3 · 한 단계만 실행 후 멈춤
"1단계만 구현. 끝나면 멈추고 변경 요약 + 테스트 결과 보고."

단계마다 검증 후 다음 단계로. 이 "멈춤" 습관이 Day2 게이트의 토대입니다.

ActivityWatch 목표 힌트 · S4 Plan·Test Matrix

ActivityWatch의 요약·타임라인·카테고리 기능은 장기 방향입니다. 이번 Plan은 그중 sessionize 한 slice만 Day2에 끝낼 수 있도록 씁니다.

  • Core plan 질문: test/activity.test.js의 skip 2개와 src/activity.js TODO를 읽고, 어떤 순서로 RED를 확인하고 최소 구현과 GREEN·gate까지 갈지 2~4단계로 직접 쓰세요.
  • Core Test Matrix 질문: fixture를 계산해 임계값 초과와 정확히 같은 경우의 기대값을 채우고, 예외 행은 기존 baseline의 무효 event 또는 collector 실패 테스트와 연결하세요.
  • Stretch 후보: 기본값은 none입니다. core와 gate가 GREEN이고 시간이 남으면 카테고리별 시간, 명시적 AFK 필터, 하루 타임라인/날짜 필터, 합성 JSON import/export 중 0개 또는 1개를 별도 backlog에 둡니다.
  • Out: 실제 watcher·브라우저 확장, 상시 백그라운드 실행, DB·전체 Web UI, ActivityWatch REST/query 완전 호환.

Day1에 적을 것: 어떤 2~4단계로 구현할지, 각 AC가 어느 테스트와 연결되는지, 실패하면 무엇을 되돌리고 어떤 명령으로 baseline을 확인할지. 코드는 아직 작성하지 않습니다.

참조 심화 — Definition of Done · 의사결정 가역성

Definition of Done: 계획의 각 단계는 Code + Test + Required Check + Doc + Rollback Path 5개가 모두 있어야 "완료"로 봅니다. Plan에 이 5개 칸을 미리 넣어 두면 누락이 사라집니다.
one-way / two-way door: 되돌리기 쉬운 two-way door(코드 초안 등)는 AI 초안으로 빠르게, 되돌리기 어려운 one-way door(아키텍처·데이터·계약·릴리스)는 사람 결정으로. risk tier를 이 기준으로 나눕니다. 2개 이상 옵션을 비교하는 ADR-lite(옵션·가역성·리스크·owner)로 기록합니다.

체크포인트 & 산출물

산출물: Plan 실행 기록(계획 → 단계별 결과), Test Matrix, risk tier + Human Gate 표시, rollback note 초안.
  • 계획이 2~4단계로 제한되고 각 단계에 stop point가 있는가?
  • Test Matrix가 AC와 1:1로 연결되는가?
  • 승인이 필요한 작업(Human Gate)과 로컬에서 끝낼 작업이 구분되었는가?
컷라인: 시간 부족 시 STEP 1~2(계획+Test Matrix)까지만. 실제 코드 실행은 Day2로 이월 가능.

흔한 실수 & 공유 포인트

실수 1 · 계획 받자마자 전 단계 일괄 실행 → 통제력 상실

계획을 "한꺼번에 다 해줘"로 넘기면 stop point가 무의미해집니다.

✗ 예시: Plan이 1) 면세 분기 2) 음수 가드 3) 반올림 정리 4) 리팩토링인데 "전부 구현해줘"로 한 번에 실행 → 테스트가 깨졌는데 어느 단계가 원인인지 알 수 없음.
✓ 교정: "1단계만 구현. 끝나면 멈추고 변경 요약 + 테스트 결과 보고." — stop point마다 npm test로 확인하고 다음 단계로.

실수 2 · rollback note를 "나중에"

되돌릴 경로는 구현 전에 있어야 실패 시 빠릅니다.

✗ 예시: calcVat() 반올림 정책을 바꿨다가 운영 청구액이 틀어졌는데, 되돌릴 커밋·설정 스냅샷을 안 적어둬 원복에 한참 걸림.
✓ 교정: 구현 전에 rollback note 초안 — 되돌릴 기준 커밋 abc1234 · 명령 git revert abc1234 · 확인 npm test(HE-10).
공유 포인트: "계획 단계에서 잡아낸 잘못된 가정"을 한 줄로 — 예: "Plan을 보다 '면세는 소수점 절사, 일반은 반올림'이라는 다른 규칙을 발견해 코드 쓰기 전에 AC를 고쳤다." 계획-실행 분리의 가치를 가장 잘 보여주는 사례입니다.
