미니강의 — SDD는 "검증 가능한 스펙 → 구현"

SDD(SD-01)는 요구사항을 정형화하고 Acceptance Criteria·Test Matrix로 검증 가능하게 만든 뒤 구현하는 방식입니다. 핵심은 순서입니다: 스펙 → 테스트 → 구현. 구현을 먼저 하면 테스트가 구현을 따라가며 의미가 약해집니다.

spec.md→실패 테스트(test-first)→사람 검토→최소 구현→로컬 테스트
RED의 이중 의미: 테스트 명령은 실패하지만 d2-s4-red checkpoint는 PASS할 수 있습니다. 이는 오류를 숨긴 것이 아니라 구현 전 테스트가 미구현 요구를 정확히 감지했다는 순서 증거입니다.

실습 1 — spec.md 정형화

spec.md 표준 형식 (SD-07)
# Feature: 집중 세션 분리 (예시)
## Context
- 비식별 스펙: 활동 이벤트 목록을 받아 유휴 간격 기준으로 집중 세션을 나눈(순수 로직)
## Requirements
- R1 유휴 간격이 임계 초과면 새 세션 / R2 임계 이하면 같은 세션(end 확장) / R3 무효 이벤트(start>=end)는 제외
## Acceptance Criteria
- AC1 유휴 간격 초과 시 세션 분리 (정상)
- AC2 간격이 정확히 임계면 같은 세션 (경계)
- AC3 public API(sessionize) 시그니처 불변
## Tests First
- activity.test.js: 세션화 2건 (현재 skip)
## Constraints
- 외부 패키지 금지, 실제 OS 수집 금지(collector 주입), allowed: src/activity.js, test/activity.test.js

실습 2 — test-first 구현

STEP 1 · 실패 테스트 먼저
[작업] test/activity.test.js의 sessionize 테스트 2개에서 { skip: true }를 {}로 바꿔 skip만 해제하라.
[제약] 테스트 이름·assertion·fixture와 구현 코드는 수정하지 마라.
[검토] npm test가 sessionize 기대값에서 2건 실패해야 정상 RED다.
[출력] 실패한 테스트 이름 + 각 테스트가 검증하는 AC 매핑.
STEP 2 · 사람이 테스트 검토

활성화한 기존 테스트가 스펙을 제대로 검증하는지 동료/PL이 확인합니다. 검토 기준: ① AC와 1:1 매핑 ② 정상·경계 케이스 분리 ③ 실패 위치가 환경·import가 아닌 sessionize 기대값. 불일치하면 assertion을 약화하지 않고 stop 후 스펙·테스트 owner에게 확인하며, 일치하면 approve 후 STEP 3으로 진행합니다.

STEP 3 · AI 첫 답 판단 후 최소 구현

AI 첫 답은 정답이 아니라 후보입니다. lab-work/implementation-decision.md에 수용/거부와 AC·테스트 근거를 먼저 기록합니다. 근거 없이 첫 답을 붙여 넣으면 checkpoint가 BLOCK됩니다.

[작업] 방금 활성화한 테스트를 통과시킬 최소 변경만 구현하라.
[규칙] AC 1개만 통과시키는 최소 코드 — 여러 AC를 한 번에 구현 금지. 통과 후 다음 AC로.
[제약] public API 유지, 외부 패키지 금지, allowed files만 수정.
[멈춤] 구현 후 테스트 결과 + diff 요약 보고하고 멈춰.
STEP 4 · 로컬 게이트
npm test        # 전체 유닛테스트 GREEN 확인
npm run gate   # lint + test + lab:selftest + policy-check

참조 심화 — 에이전트 SDLC 경계 & 추적성

3층 책임 모델

기록 시스템(로컬 Git, PR 대체)→Copilot = 보조 레이어→사람 = 승인 경계
AI 레드라인: 에이전트는 merge·release·publish·rollback 승인, 보안 go/no-go, 아키텍처·데이터 결정, 고객 데이터·secret 취급을 할 수 없습니다. "AI 초안 → 사람 검토 → 정책 강제."

추적성 · 로컬 버전

원격 PR이 없으므로 스펙 ↔ 브랜치 ↔ 커밋 ↔ 로컬 체크 ↔ 리뷰어를 패킷으로 연결합니다(요구사항 추적성 SD-13). 모든 변경이 어느 AC에서 왔는지 추적되어야 합니다.

BDD 브래킷: 단계를 Given-When-Then 문장으로 열고, 같은 문장 + 증거 링크로 닫습니다. AC는 SMART + 측정 source가 명시되어야 합니다.

실습에서 기대하는 바와 결과 예시

기대하는 바

  • skip만 해제해 구현 전 테스트가 요구사항 때문에 실패하는 RED를 확인한다.
  • AI 첫 답을 AC·테스트 근거로 수용·거부한 뒤 allowed files에 최소 구현한다.
  • RED와 GREEN을 각각 독립 evidence로 남긴다.

RED 결과 예시

activity.test.js: 5 pass / 0 skip / 2 fail
실패 위치: sessionize 기대값
checkpoint d2-s4-red: PASS
구현 변경: 없음

GREEN 결과 예시

판단: AI 후보 revise 후 수용
근거: AC1·AC2와 경계 테스트 일치
activity.test.js: 7 pass / 0 skip / 0 fail
checkpoint d2-s4-green: PASS
예시 해석: RED의 테스트 실패는 checkpoint 실패가 아닙니다. 구현 없이 요구사항 결손을 정확히 감지해야 RED checkpoint가 PASS하며, 구현 코드는 예시를 복사하지 않고 테스트 근거로 직접 완성합니다.

체크포인트 & 산출물

산출물: spec.md + 실패 테스트(검토 완료) + 스펙 기반 최소 구현(allowed files 내).
  • test-first 순서가 지켜졌는가?
  • 각 테스트가 AC와 매핑되는가?
  • 구현이 allowed files 안에서만 이루어졌는가?
컷라인: must-have AC 1개에 대한 실패 테스트 → 구현 → 통과 1사이클이면 통과입니다.

흔한 실수 & 공유 포인트

  • 구현부터 하고 테스트를 나중에 → SDD가 아님. 테스트를 먼저.
  • Copilot 테스트를 그대로 신뢰 → 반드시 사람이 검토합니다.
공유 포인트: "스펙 한 줄 ↔ 테스트 한 줄"의 추적성(SD-13) 사례. SDD의 가치를 가장 명확히 보여줍니다.
