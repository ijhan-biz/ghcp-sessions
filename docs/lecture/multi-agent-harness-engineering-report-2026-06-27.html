멀티에이전트 하네스 엔지니어링 라이브러리·방법론·스택 비교

Superpowers, Compound Engineering, gstack을 포함해 멀티에이전트 작업을 더 안전하고 검증 가능하게 만드는 방법론, 런타임, 평가 도구, 관측성, 정책 게이트를 비교한 실사용 중심 보고서입니다.

요약 결론

핵심 판단: 멀티에이전트 하네스는 단일 프레임워크 하나로 끝나는 문제가 아니라, 역할 분리, 실행 격리, 평가, 관측성, 정책, 회고 메모리를 엮은 운영 체계입니다. Superpowers와 gstack은 “에이전트에게 좋은 엔지니어링 습관을 강제하는 스킬/워크플로우”에 가깝고, Compound Engineering은 “학습을 다음 세션에 다시 주입하는 방법론”입니다. 실제 제품 하네스는 여기에 LangGraph, OpenAI Agents SDK, AutoGen, CrewAI 같은 런타임과 promptfoo, Inspect, DeepEval, Ragas, LangSmith, Langfuse, Phoenix 같은 평가/관측 도구를 조합해야 합니다.

1. 워크플로우 계층 Superpowers Compound Engineering gstack

기획, 작업 분해, TDD, 리뷰, QA, 회고를 에이전트가 반복 가능한 절차로 따르게 만듭니다. 공식 README와 문서 기준으로 Superpowers는 composable skills와 TDD 중심, gstack은 23개 specialist와 slash command 중심, Compound Engineering은 Plan-Work-Assess-Compound 루프 중심입니다. [S1][S3][S5]

2. 런타임/오케스트레이션 계층 LangGraph OpenAI Agents SDK AutoGen CrewAI

상태, handoff, tool use, sandbox, memory, human-in-the-loop을 코드로 다룹니다. 프로덕션 제어가 필요하면 runtime을 명시적으로 선택해야 합니다. [S7][S8][S9][S10]

3. 검증/운영 계층 promptfoo Inspect Langfuse OPA

품질을 “느낌”이 아니라 데이터셋, assertion, trace, policy, CI exit code로 판단합니다. 이 계층이 없으면 멀티에이전트는 빨라질 수는 있어도 반복 가능하다고 말하기 어렵습니다. [S12][S14][S17][S20]

범위와 판단 기준

이 보고서에서 말하는 하네스

멀티에이전트 하네스는 모델 자체가 아니라, 여러 에이전트가 일하는 환경과 검증 체계입니다. 보통 다음 구성요소를 포함합니다.

  • 역할 정의: planner, implementer, reviewer, QA, security, release 등
  • 실행 격리: branch, worktree, sandbox, container, browser session
  • 작업 계약: spec, plan, task graph, acceptance criteria, schema
  • 검증 게이트: tests, evals, browser QA, policy, security scan
  • 관측성: trace, transcript, cost, latency, tool call, artifact lineage
  • 학습 루프: 실패 사례를 instruction, skill, eval dataset으로 승격

비교 기준

  • 반복 가능성: 같은 입력에서 같은 절차와 산출물이 나오는가
  • 검증 가능성: 성공/실패를 사람이 아닌 기계가 판단할 수 있는가
  • 격리와 안전: agent별 권한, 파일 범위, destructive action을 제한할 수 있는가
  • 관측성: 왜 실패했는지 trace와 artifact로 되짚을 수 있는가
  • 학습 지속성: 리뷰와 장애에서 배운 점이 다음 실행에 반영되는가
  • 도입 난이도: 기존 repo와 팀 워크플로우에 붙이기 쉬운가

도구·방법론 비교표

대상 분류 근거 기반 핵심 사실 하네스에서 좋은 위치 주의점
Superpowers 에이전트 스킬 프레임워크·방법론 Claude Code, Codex CLI/App, Factory Droid, Gemini CLI, OpenCode, Cursor, GitHub Copilot CLI를 지원한다고 설명한다. 기본 워크플로우는 brainstorming, git worktrees, writing plans, subagent-driven development/executing plans, TDD, code review, finishing branch이다. [S1] TDD, 계획, subagent task execution, code review를 agent 기본 습관으로 강제하는 상위 워크플로우 정량 eval/trace/policy 엔진은 아니므로 promptfoo, Playwright, OPA 같은 게이트와 결합해야 한다.
Compound Engineering 방법론·학습 루프 Every는 Plan, Work, Review, Compound 루프를 설명하며, agent가 작성한 코드와 학습을 다시 시스템에 주입한다고 설명한다. AgentPatterns는 Plan 40%, Work 20%, Assess 30%, Compound 10% 배분과 `/ce:plan`, `/ce:work`, `/ce:review`, `/ce:compound` 플러그인 명령을 소개한다. [S3][S4] 회고와 리뷰 결과를 instruction, prompt, skill, eval dataset으로 승격시키는 운영 원칙 프롬프트 파일이 오래되거나 모순되면 오히려 agent를 혼란스럽게 할 수 있다. [S4]
gstack 역할 기반 스킬 스택·브라우저/QA/릴리스 워크플로우 README는 gstack이 Claude Code를 virtual engineering team으로 바꾸며 23 specialists와 8 power tools, Think → Plan → Build → Review → Test → Ship → Reflect 흐름을 제공한다고 설명한다. `/qa`, `/review`, `/ship`, `/cso`, `/codex`, `/browse`, `/learn`, `/pair-agent` 등 명령이 있다. [S5] 제품 개발 sprint harness, browser QA, security review, release gate, cross-model review, memory loop 공식 표기는 `gstack`이다. 사용자가 말한 “g-stack”이 같은 대상을 뜻하는지는 문맥상 높지만, 일반 표준명으로 확정하지 않는다.
Spec Kit Spec-driven development 툴킷 specification을 실행 가능한 산출물로 보고 `/speckit.constitution`, `/speckit.specify`, `/speckit.plan`, `/speckit.tasks`, `/speckit.implement` 흐름을 제공한다. 30개 이상 AI coding agent integration과 extension/preset 생태계를 설명한다. [S24] acceptance criteria, task graph, governance constitution, CI guard 같은 하네스 입력 산출물 생성 실행 agent 품질 자체를 보장하지 않는다. 검증 계층과 함께 써야 한다.
LangGraph 상태형 agent 오케스트레이션 long-running, stateful agents를 위한 low-level orchestration framework이며 durable execution, streaming, human-in-the-loop, memory, LangSmith debugging을 강조한다. [S7] 상태 machine, supervisor-worker, retry/resume, human approval이 필요한 agent workflow runtime 낮은 수준의 runtime이므로 평가와 정책은 별도 설계해야 한다.
OpenAI Agents SDK agent runtime·handoff·guardrail Agents, handoffs/agents-as-tools, guardrails를 핵심 primitive로 제공하며 built-in agent loop, sandbox agents, MCP tool calling, sessions, human-in-the-loop, tracing을 제공한다고 설명한다. [S8] Python-first multi-agent runtime, sandboxed coding/review agent, guardrail과 tracing이 필요한 OpenAI 중심 stack OpenAI stack과 친화적이다. multi-provider를 써도 조직의 모델 전략과 비용 정책을 별도 정해야 한다.
AutoGen multi-agent framework AgentChat은 conversational single/multi-agent app, Core는 scalable multi-agent AI systems를 위한 event-driven framework라고 설명한다. Docker code executor와 gRPC distributed agents 확장도 언급한다. [S9] 연구, 실험, 분산 multi-agent workflow, code execution sandbox가 필요한 Python stack 프로덕션 하네스에서는 governance, eval, trace, policy를 명시적으로 보강해야 한다.
CrewAI crew/flow 기반 multi-agent framework 공식 문서는 collaborative AI agents, crews, flows를 구축하고 guardrails, memory, knowledge, observability가 내장되어 있다고 설명한다. [S10] 역할 기반 팀 자동화, 운영 workflow, enterprise automation을 빠르게 구성 세부 검증과 policy gate는 사용자의 process에 맞게 추가해야 한다.
MCP tool/data 연결 표준 AI application을 local files, database, search, calculator, specialized prompts 같은 external systems에 연결하는 open-source standard라고 설명한다. [S23] 하네스의 도구 계층 표준화, agent별 tool allowlist, external tool wrapping MCP 자체는 정책이나 검증을 대신하지 않는다. 어떤 server를 허용할지 governance가 필요하다.
promptfoo LLM eval·red team CLI/library open-source CLI/library for evaluating and red-teaming LLM apps로, declarative test cases, metrics, caching, concurrency, CI/CD, red teaming을 제공한다. [S12] prompt/model/RAG/agent output regression, CI pass/fail, red-team smoke test tool trajectory 전체 평가보다 prompt/output matrix 평가에 강하다. 복잡한 agent trace는 별도 수집이 필요하다.
OpenAI Evals LLM/LLM system evaluation framework LLM 또는 LLM system을 평가하는 framework와 benchmark registry를 제공하며 custom eval, private eval, completion function protocol을 설명한다. [S11] 모델 변경 전후 benchmark, private workflow eval, tool-using agent completion function 평가 레지스트리와 실행 비용, 데이터 권리, OpenAI API 사용 조건을 관리해야 한다.
Inspect AI frontier AI eval framework UK AI Security Institute와 Meridian Labs가 개발한 framework이며 coding, agentic tasks, reasoning 등을 평가하고 200개 이상 pre-built eval, agents, multi-agent primitives, external agents, sandboxing을 지원한다고 설명한다. [S14] 고위험 agent eval, sandboxed tool use, multi-agent benchmark, 연구/보안 평가 초기 설정과 task/scorer 설계가 필요하다. 간단한 prompt matrix에는 다소 무겁다.
DeepEval LLM eval·tracing local eval, `deepeval test run`, GEval, LLM test case, component-level tracing, agent 내부 span 평가, online eval을 설명한다. [S13] pytest 스타일 agent regression, component-level scoring, Confident AI 연동 dashboard 많은 metric이 LLM-as-judge이므로 judge 모델 drift와 비용을 관리해야 한다.
Ragas RAG/agent eval loop vibe checks를 systematic evaluation loops로 바꾸는 library라고 설명하며 experiments, metrics, datasets, LangChain/LlamaIndex integration, agent tool-use metrics를 제공한다. [S16] RAG, tool-call accuracy, answer faithfulness, synthetic testset generation RAG/LLM app 품질 평가에 강하며, 소스코드 보안/브라우저 QA는 다른 도구가 필요하다.
LangSmith evaluation·tracing platform offline eval은 dataset/examples, online eval은 production runs/threads를 대상으로 하며, evaluator는 human, code, LLM-as-judge, pairwise 방식을 지원한다고 설명한다. [S6] LangChain/LangGraph 기반 agent의 dataset regression, production trace monitoring, annotation queue LangChain ecosystem과 함께 쓸 때 가장 자연스럽다.
Langfuse LLM observability·prompt·eval platform open-source LLM engineering platform으로 traces, prompt management, evaluation, datasets, experiments를 제공하며 OpenTelemetry 기반 호환성을 강조한다. [S17] trace, cost/latency, prompt versioning, production eval dashboard 정책 enforcement 자체보다는 관측과 평가 UI에 가깝다.
Phoenix AI observability·evaluation Phoenix는 traces, evaluation tests, prompt iteration, experiments를 통해 AI app 디버깅과 개선 workflow를 제공하며 OpenTelemetry와 OpenInference instrumentation 위에 구축되었다고 설명한다. [S18] open-source trace/eval UI, production examples 기반 prompt iteration 하네스 pass/fail 기준은 별도 scorer와 CI 연결이 필요하다.
OpenTelemetry vendor-neutral observability standard traces, metrics, logs를 instrument, generate, collect, export하는 vendor-neutral open-source framework라고 설명한다. [S19] agent_id, role, tool_call, cost, trace_id를 표준 telemetry로 남기는 기반 LLM 특화 UI/metric은 Langfuse, Phoenix, LangSmith 같은 도구가 보강한다.
Playwright browser automation·E2E test modern web apps를 위한 E2E test framework이며 runner, assertions, isolation, parallelization, tooling을 번들로 제공하고 Chromium/WebKit/Firefox를 지원한다. [S15] agent가 만든 웹 UI의 실제 browser regression, screenshot/trace evidence LLM 품질 평가는 하지 않는다. agent output 평가와 함께 써야 한다.
OPA policy-as-code engine policy decision-making을 enforcement에서 분리하고, JSON 같은 structured input을 받아 Rego policy와 data로 decision을 생성한다. CI/CD, microservices, Kubernetes 등에 사용된다고 설명한다. [S20] agent action allow/deny, tool permission, egress, artifact completeness, release gate 정책은 명확한 구조화 입력이 있을 때 가장 잘 작동한다. transcript free text에는 별도 parser가 필요하다.
Semgrep SAST/SCA/secrets scan bugs, reachable dependency vulnerabilities, code standards를 every commit에서 enforce하며 SAST, SCA, secrets scan을 제공한다고 설명한다. [S21] agent-authored PR 보안/품질 기본 게이트, custom rules runtime behavior나 LLM hallucination은 직접 평가하지 않는다.
CodeQL semantic code analysis code를 data처럼 query하여 vulnerability variants를 찾는 도구로 설명한다. [S22] 고위험 code path와 보안 취약점 검출, GitHub code scanning 초기 query와 language support 범위를 확인해야 한다.
Guardrails AI + Pydantic input/output validation·schema Guardrails는 LLM input/output guards와 structured data generation을 제공한다. Pydantic은 Python type hint 기반 validation, serialization, JSON Schema, strict/lax mode를 제공한다. [S25][S26] agent output contract, JSON report schema, tool argument validation, safety validators 품질 평가라기보다는 구조/위험 validation이다. semantic correctness는 eval metric이 필요하다.

핵심 대상 상세 분석

Superpowers: 에이전트에게 SDLC 습관을 강제하는 스킬 레이어

사실: Superpowers README는 “complete software development methodology for your coding agents”라고 설명하며, TDD, systematic debugging, verification-before-completion, brainstorming, writing plans, executing plans, dispatching parallel agents, code review, git worktrees, subagent-driven development 같은 skills library를 나열한다. [S1]

하네스 해석: Superpowers는 agent runtime이라기보다 workflow discipline입니다. agent가 바로 코드를 쓰지 않고, 의도 확인 → worktree 격리 → 작은 task 계획 → TDD → 리뷰 → branch 완료를 거치게 하므로 “멀티에이전트가 제멋대로 흩어지는 문제”를 줄이는 데 유리합니다.

실사용 예시: 신규 기능을 만들 때 먼저 `/superpowers:brainstorm`으로 요구사항을 분해하고, 승인된 design doc을 기준으로 `writing-plans`가 2-5분 단위 task를 만든 뒤, `subagent-driven-development`가 task별 fresh context subagent를 dispatch합니다. 이후 `requesting-code-review`가 plan 대비 결함을 severity별로 보고하고, critical issue는 진행을 막습니다. Better Stack의 x-dl web UI 사례는 Superpowers 방식이 상세 설계, TDD, subagent execution, review를 거쳐 download behavior와 UI 품질을 개선했다고 설명합니다. [S2]

Compound Engineering: 배운 점을 다음 agent 실행의 입력으로 바꾸는 루프

사실: Every는 compound engineering loop를 Plan, Work, Review, Compound로 설명하고, bug, failed test, problem-solving insight를 문서화해 future agents가 사용하게 한다고 설명한다. AgentPatterns는 이를 Plan-Work-Assess-Compound 루프로 정리하고, learnings를 repo prompt로 encode한다고 설명한다. [S3][S4]

하네스 해석: 멀티에이전트의 가장 큰 손실은 같은 실수를 세션마다 반복하는 것입니다. Compound Engineering은 리뷰 결과를 instruction, skill, eval, policy로 승격시키는 “학습 승격 프로세스”로 쓰는 것이 핵심입니다.

실사용 예시: QA agent가 “migration timestamp 순서 오류”를 찾았다면, 단순 bugfix에서 끝내지 않고 `agent-learnings/migrations.md`에 context, rule, example 형식으로 저장합니다. 다음 sprint의 planner/reviewer agent는 이 파일을 읽고 migration task를 생성할 때 dependency order check를 포함합니다. 동시에 eval dataset에는 “migration with FK dependency” golden case를 추가합니다.

gstack: 역할 기반 startup engineering squad를 slash command로 구현

사실: gstack README는 23 specialists와 8 power tools를 통해 CEO, eng manager, designer, reviewer, QA lead, security officer, release engineer 역할을 제공한다고 설명한다. `/qa`는 real browser를 열어 flow를 테스트하고 regression test를 생성한다고 설명하며, `/pair-agent`는 여러 agent가 공유 browser에서 각자 tab을 가지고 협업하는 기능을 설명한다. [S5]

하네스 해석: gstack은 “agent team을 어떻게 운영할지”에 대한 가장 제품화된 예시에 가깝습니다. 특히 `/browse`, `/qa`, `/cso`, `/codex`, `/learn`, `/ship`은 하네스의 검증/안전/회고 계층과 직접 맞닿아 있습니다.

실사용 예시: product feature를 만들 때 `/office-hours`로 문제 재정의, `/autoplan`으로 CEO/design/eng/DX review, 구현 후 `/review`와 `/codex`로 cross-model review, `/qa https://staging...`로 실제 browser QA, `/cso`로 OWASP/STRIDE 검토, `/ship`으로 test/coverage/PR, `/learn`으로 반복 학습을 관리하는 흐름을 구성할 수 있습니다.

Spec Kit: 하네스 입력 산출물을 안정화하는 spec-first 계층

사실: Spec Kit은 specification을 executable artifact로 보고 constitution, specify, plan, tasks, implement commands를 제공한다. 또한 community extension에는 MAQA, CI Guard, QA Testing, Superpowers Bridge, Squad Bridge 같은 하네스 연계 항목이 존재한다. [S24]

하네스 해석: Superpowers/gstack이 실행 습관을 다룬다면, Spec Kit은 agent가 따라야 할 산출물 계약을 만듭니다. 멀티에이전트가 동시에 달릴수록 spec, plan, task, acceptance criteria의 안정성이 중요합니다.

    "harness:eval": "promptfoo eval --config evals/promptfooconfig.yaml --output output/promptfoo.json",
    "harness:browser": "playwright test",
    "harness:security": "semgrep scan --config p/owasp-top-ten --json --output output/semgrep.json",
    "harness": "npm run harness:schema && npm run harness:policy && npm run harness:eval && npm run harness:browser && npm run harness:security"
  }
}

운영 방식: planner, implementer, reviewer, QA agent가 작업을 수행하되 최종 완료는 `npm run harness`가 통과할 때만 허용합니다. 이 패턴은 promptfoo의 CI/eval, Playwright의 E2E, OPA의 policy-as-code, Semgrep의 security gate를 결합합니다. [S12][S15][S20][S21]

예시 B: Superpowers + Spec Kit + eval stack

팩트, 해석, 불확실성

확인된 사실

  • Superpowers는 여러 coding agent에서 동작하는 skills 기반 software development methodology로 자신을 설명한다. [S1]
  • Compound Engineering은 Plan, Work, Review/Assess, Compound의 closed loop로 설명되며, learnings를 repo prompt/instruction으로 저장하는 방식이 핵심이다. [S3][S4]
  • gstack은 role-based slash command stack이며 browser QA, security review, release, learn, cross-agent/cross-model 흐름을 포함한다. [S5]
  • LangSmith, Langfuse, Phoenix는 production trace와 evaluation loop를 연결하는 LLM observability/evaluation 도구다. [S6][S17][S18]
  • OPA, Semgrep, CodeQL, Guardrails, Pydantic은 agent output과 code artifact에 deterministic policy/security/schema gate를 거는 데 활용할 수 있다. [S20][S21][S22][S25][S26]

연구 해석

  • 하네스의 핵심은 “똑똑한 agent”보다 “실패를 작게 만들고 관측 가능하게 만드는 환경”이다.
  • Superpowers와 gstack은 개발자 경험을 빠르게 끌어올리는 상위 workflow이고, LangGraph/OpenAI Agents SDK/AutoGen/CrewAI는 직접 제품 agent를 만들 때 필요한 runtime이다.
  • 평가 도구는 하나만 고르기보다 output eval, trajectory trace, browser QA, policy gate를 나누어 쓰는 편이 안정적이다.
  • Compound Engineering은 별도 도구보다 운영 습관에 가깝다. 그러나 하네스 artifact에 반영하면 장기 품질 개선 효과가 크다.

불확실성과 주의사항

  • “g-stack”이라는 표기는 조사 중 독립 표준명으로 확인되지 않았다. 이 보고서는 공식 GitHub repository 이름인 `garrytan/gstack`을 기준으로 다룬다.
  • GitHub star, fork, 최신 commit 같은 popularity 지표는 시점에 따라 변한다. 이 보고서의 추천은 popularity보다 기능 적합성에 근거한다.
  • LLM-as-judge 기반 eval은 judge prompt, judge model, 비용, drift를 관리해야 한다. deterministic test를 완전히 대체하지 않는다.
  • AgentPatterns.ai의 Compound Engineering 설명은 패턴 카탈로그 성격이다. Compound Engineering의 원 출처로는 Every article을 우선 참고했다.
  • 공식 문서가 “production-ready”라고 표현해도, 각 조직의 보안, privacy, compliance, data retention 요구사항은 별도로 검토해야 한다.

권장 실행 계획

  1. 1주차: 현재 repo에 `harness/report.schema.json`, `harness/check-report.*`, `output/round-report.json` 형식부터 만든다. 완료 조건을 말이 아니라 JSON schema와 tests로 고정한다.
  2. 2주차: promptfoo 또는 DeepEval로 agent output regression을 붙이고, Playwright로 user-facing flow를 최소 3개 만든다.
  3. 3주차: OPA policy를 추가해 destructive action, missing evidence, unapproved external URL, missing reviewer 같은 운영 위반을 fail-closed로 막는다.
  4. 4주차: Langfuse/Phoenix/LangSmith 중 하나로 trace를 수집하고, 실패 trace를 eval dataset과 instruction learning으로 승격한다.
  5. 지속: Superpowers/gstack/Spec Kit 중 팀에 맞는 workflow layer를 붙여 사람의 운영 습관을 agent가 따르는 기본 절차로 만든다.
