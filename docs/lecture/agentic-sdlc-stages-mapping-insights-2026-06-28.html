1. Agentic SDLC란

Agentic SDLC는 라이프사이클의 각 단계를 사람이 직접 수행하는 대신, 의도(명세)를 받아 에이전트가 탐색·구현·검증을 수행하고 사람은 방향 설정·검토·승인을 맡는 개발 생애주기다. 핵심 전제는 다음과 같다.

  • 명세 우선(Spec-Driven): 기계가 읽을 수 있는 명세가 에이전트 작업의 단일 기준이 된다. 구조 없는 "그냥 만들어줘"(vibe coding)와 대비된다.
  • 통제면 우선(Harness over Prompt): 결과 품질은 "좋은 프롬프트"보다 도구 오케스트레이션·권한·컨텍스트·검증·복구·관측이라는 통제 아키텍처가 좌우한다.
  • 사람 검토 유지(Human-in-the-loop): 자율성이 커져도 merge/deploy 같은 결정은 정책과 사람 검토 게이트를 통과한 뒤에만 이뤄진다.
  • 폐루프(Closed Loop): 운영 피드백이 다시 명세로 돌아와 다음 라운드를 개선한다 — 단발 생성이 아니라 지속 개선 루프.
전통 SE 개념은 사라지지 않는다. DDD·BDD·TDD·DevOps·SRE는 여전히 토대이며, Agentic은 그 위에 통제·검증·자동화 층을 더하는 것이다.

핵심 개념 깊게 보기 — 역사·배경·근거·사용예

Agile 2001

역사 2001년 17인의 Agile Manifesto 발표가 공통 기점.

배경 문서 중심·장기 계획형 폭포수의 변화 대응 실패.

근거 Agile Manifesto(agilemanifesto.org)의 4가치·12원칙.

사용예 2주 스프린트로 우선순위 높은 기능부터 동작하는 SW를 전달하고 회고로 개선.

DDD 2003

역사 Eric Evans의 2003년 저서 《Domain-Driven Design》.

배경 복잡한 업무 도메인과 코드 모델의 괴리.

근거 Evans 저서, Martin Fowler의 Ubiquitous Language·Bounded Context 정리.

사용예 보험 청구 도메인을 청구·심사·지급 Bounded Context로 나눠 각자 일관된 모델 유지.

TDD ≈1999–2003

역사 Kent Beck이 XP와 함께 대중화, 2002 《TDD: By Example》.

배경 회귀 버그와 설계 경직성.

근거 Beck 저서, XP 실천.

사용예 실패 테스트를 먼저 쓰고 통과시킨 뒤 리팩터링으로 설계 개선.

BDD 2003–2006

역사 2003~2004년 실천·도구(JBehave)로 형성, Dan North의 2006년 글로 널리 정리.

배경 “무엇을 테스트할지” 모호성과 비개발자 소통 단절.

근거 Dan North ‘Introducing BDD’, Cucumber의 Discovery–Formulation–Automation.

사용예 “장바구니에 담고 결제하면 재고가 준다”를 Given-When-Then 시나리오로.

DevOps 2009

역사 Patrick Debois 주도 첫 DevOpsDays(2009)에서 용어 확산.

배경 개발-운영 사일로와 책임 전가.

근거 DevOpsDays, 이후 Accelerate/DORA 연구.

사용예 개발팀이 IaC·온콜·SLO까지 소유해 전달 흐름을 끝에서 끝까지 책임.

Continuous Delivery 2010

역사 Jez Humble · David Farley의 2010 저서 《Continuous Delivery》.

배경 길고 위험한 수동 릴리즈.

근거 Humble·Farley 저서, deployment pipeline 개념.

사용예 모든 커밋이 자동 파이프라인을 통과해 언제든 배포 가능한 상태 유지.

SRE Google · 2016 공개서

역사 Google 내부에서 먼저 발전, 2016년 공개서 《Site Reliability Engineering》으로 확산(실천 시작과 출간은 구분).

배경 신뢰성을 사람의 영웅이 아니라 공학·예산으로.

근거 Google SRE 서적, Error Budget 개념.

사용예 SLO 99.9% + Error Budget 소진 시 신기능보다 안정화를 우선.

ADR 2011

역사 Michael Nygard의 2011 글 ‘Documenting Architecture Decisions’.

배경 시간이 지나면 결정 이유가 사라지는 문제.

근거 Nygard 글, Thoughtworks Tech Radar의 Lightweight ADR 권장.

사용예 “PostgreSQL 선택” 결정의 맥락·대안·결과를 repo에 .md로 보관.

EventStorming 2013

역사 Alberto Brandolini가 제안한 도메인 탐색 워크숍.

배경 복잡한 업무 흐름에서 경계·용어가 보이지 않는 문제.

근거 DDD/EventStorming 커뮤니티 자료.

사용예 주문→재고차감→배송 같은 도메인 이벤트를 붙여 경계를 발견.

MCP · Agentic 2024–2026

역사 2024 Anthropic MCP 공개, 2025–26 Spec-Driven·Agentic DevOps·Harness Engineering 논의 확산.

배경 프롬프트 의존의 한계와 정책·검증 통제의 필요.

근거 내부 정리 및 Anthropic MCP 공개 표준(MCP=데이터·도구 연결용 개방 표준).

사용예 MCP로 도구·데이터에 표준 연결하고, 그 위에 정책·승인·감사를 별도 설계해 명세 기준 검증.

A. 요구사항 발견·정의

  • Requirements Engineering (RE) — 요구사항을 수집·분석·명세·검증·변경관리까지 체계화하는 기반 디시플린. 요구 누락·상충·추적 불가 문제를 막는다. 규제 산업·대규모·이해관계자가 많은 시스템에서 필수. BDD/DDD를 써도 RE가 약하면 추적성과 승인 경로가 무너진다.
  • Behavior-Driven Development (BDD) — 요구를 구체적 행위 예시(Given-When-Then)로 정의해 비즈니스·개발·QA가 공통 언어로 합의하는 협업 프로세스. 모호성 제거·환각 방지·Living Documentation이 핵심 가치다. Discovery–Formulation–Automation의 반복으로 이어진다.
  • Specification by Example / Example Mapping — 추상적 요구 대신 예시로 논의해 “이 말이 무슨 뜻이지” 해석 차를 제거한다. 승인 규칙·예외 케이스가 중요한 기능에 적합. BDD가 협업 프로세스라면 SbE는 예시 중심 명세화 원칙에 가깝다.
  • Event Storming — “무슨 데이터가 있나”보다 “무슨 사건이 일어나나”로 도메인을 탐색하는 워크숍. 이벤트·커맨드·정책·행위자·Bounded Context를 공동 발견한다. DDD 도입 전, 복잡한 상태 전이와 경계 발견에 유용.
  • EARS (정형 요구 패턴) — 요구 문장을 정형 패턴으로 써 모호성을 줄인다. SI/엔터프라이즈 문서, 안전·규제 요구가 많은 프로젝트의 RE 보완 도구.
  • User Story · Acceptance Criteria — 작업 단위(스토리)와 완료를 판정하는 검증 가능한 조건. INVEST(독립·협상·가치·추정·작음·테스트 가능)로 좋은 스토리를 판단한다.
  • Systems Thinking — 기능 하나가 아니라 전체 피드백 루프·병목·부작용을 본다. 각 단계 최적화가 전체 성능을 망치는 현상을 막는다.

B. 설계·아키텍처

  • Domain-Driven Design (DDD) — 도메인 전문가와 공유하는 보편 언어(Ubiquitous Language)와 경계 컴텍스트(Bounded Context)로 복잡한 도메인을 모델링한다. BDD가 외부 행동을 합의하면 DDD는 내부 경계를 구조화한다.
  • Clean / Hexagonal Architecture — 도메인을 프레임워크·인프라에서 분리해 의존성이 안쪽(도메인)으로만 향하게 한다. DDD가 “무엇을 모델링하는가”라면 Clean/Hexagonal은 “의존성을 어떻게 통제하는가”이다.
  • ADR (Architecture Decision Records) — 중요한 기술 의사결정의 맥락·대안·결과와 “왜(why)”를 경량으로 기록해 소스 제어에 함께 보관한다. 시간이 지나면 왜 그 구조를 골랐는지 사라지는 문제를 막는다.
  • Threat Modeling — 설계 단계에서 공격 표면과 위협 시나리오(STRIDE 등)를 모델링한다. 보안이 배포 전 스캔에서만 발견되는 문제를 앞단으로 당긴다.
  • Evolutionary Architecture — 증분적·비파괴적 변화가 가능한 구조. 마이크로서비스는 목적이 아니라 변화 용이성을 위한 수단일 뿐이다.
  • SOLID · GRASP — 단일책임·개방폐쇄·리스코프 치환·인터페이스 분리·의존 역전(SOLID)과 책임 할당 패턴(GRASP)으로 결합도를 낮춘다.

C. 구현·품질

  • Test-Driven Development (TDD) — 실패 테스트→구현→리팩터의 Red-Green-Refactor 주기로 설계를 견인한다. 단, AI가 테스트를 쓸 때 과도한 Mock(런던식 편향)이 생길 수 있어 state/result 검증을 보강해야 한다.
  • Test Pyramid · ATDD · Contract Testing — 단위>통합>E2E 비율로 빠르고 안정적인 테스트 구성(Pyramid), 완료 기준을 인수 테스트로 먼저 합의(ATDD), 서비스 간 계약을 소비자/제공자 양쪽에서 검증(Contract).
  • Shift-left Testing — 테스트·품질·보안 활동을 구현 이후가 아니라 요구/설계 초기로 끌어온다. 결함 발견이 빠를수록 수정 비용이 적다.
  • Refactoring · Pair/Mob Programming — 외부 동작을 바꾸지 않고 내부 구조를 개선(Refactoring), 둘·다수가 한 작업을 공동 검토(Pair/Mob). AI 시대엔 “Human+Agent pair”로 재해석된다.

D. 배포·운영

  • CI/CD · GitOps · IaC — 자주 통합해 자동 빌드·테스트(CI), 언제든 배포 가능 상태 유지(CD), Git을 단일 진실원으로 선언 상태 동기화(GitOps), 인프라를 선언적 코드로 관리(IaC).
  • Progressive Delivery · Feature Flags — Blue-Green·Canary·Rolling·기능 플래그로 위험을 통제하며 점진적으로 출시한다.
  • DevSecOps · Policy-as-Code — 보안을 파이프라인에 내재화하고, 정책을 코드로 선언해 자동 강제한다.
  • SRE · SLI/SLO · Error Budget — 신뢰성을 공학 문제로 다루고(SRE), 지표·목표·허용 실패 예산으로 변경 속도와 안정성을 균형한다.
  • Observability · Chaos · Resilience — 로그·메트릭·트레이스로 내부 상태를 추론하고, 고의 장애 주입(Chaos)으로 복원력 가설을 검증하며, Retry·Circuit Breaker·Bulkhead로 장애 전파를 차단한다.

E. 비용·플랫폼

  • FinOps · GreenOps — 운영 후 비용 최적화가 아니라 설계·배포 단계로 비용·탄소 의사결정을 당긴다(비용 shift-left).
  • Platform Engineering · IDP · Golden Path — DevOps 성공 이후 늘어난 인지 부하를 줄이기 위해 내부 개발자 플랫폼(IDP)과 사전 구성된 안전 경로(Golden Path)를 제품화한다. 팀 수가 늘면 선택이 아니라 규모의 문제가 된다.
  • Conway's Law · Team Topologies · DORA — 시스템 구조는 조직 소통 구조를 닮고(Conway), 그에 맞춰 팀을 설계하며(Topologies), 배포 빈도·리드타임·실패율·복구시간(DORA)으로 전달 성과를 측정한다.

F. 에이전트·AI 운영

  • Spec-Driven Development (SDD) — 사람이 검토 가능한 명세와 기계가 활용 가능한 구조화 입력을 중심으로 개발을 조직하는 접근. 구조 없는 “그냥 만들어줘”(vibe coding)와 대비되나, 아직 단일 업계 표준 정의가 확정된 용어는 아니다.
  • Agentic DevOps — 지능형 에이전트가 생명주기 각 단계를 자동화·최적화하는 DevOps의 다음 진화(Microsoft Azure 등 벤더 비전과 부합). Intent→구현→검토/테스트→배포→모니터/피드백 폐루프로 동작하나, 아직 산업 합의 교과서 정의로 단정하기는 이르다.
  • Harness Engineering — 본 문서에서는 에이전트의 도구·권한·검증·관측·복구를 체계적으로 설계하는 실무 운영 프레임을 가리킨다(도구 오케스트레이션·권한/제약·컨텍스트 관리·검증/피드백·복구·Observability 6개 레이어, 또는 Control·Observe·Verify 3축). 아직 보편 표준 학술 용어라기보다 운영 설계 관점에 가깝다.
  • MCP (Model Context Protocol) — AI 애플리케이션이 외부 데이터 소스·도구에 표준 방식으로 연결되도록 하는 개방형 프로토콜이다. 조직은 이 연결 지점 위에 정책·권한·감사·승인 체계를 별도로 설계해 통제면을 구현한다(MCP 자체가 정책 주입 표준은 아니다).
  • Human-in-the-loop · LLMOps — 자율성이 커져도 merge/deploy는 정책·사람 검토 게이트를 거친다(HITL). 모델·프롬프트·평가·안전 운영을 체계화한다(LLMOps).

3. 핵심 폐루프 (Agentic DevOps Loop)

여러 자료가 공통적으로 제시하는 에이전트 개발의 폐루프는 다음과 같다.

Intent 분석→ 명세(Spec)→ 구현(Coding)→ 검토·테스트→ 배포→ 모니터·피드백↺ Spec 갱신

각 화살표 지점마다 권한 제약·정책 주입·검증 게이트(harness)가 붙어 에이전트의 자율 실행을 통제한다.

4. 전통 SDLC 단계 + Agentic 운영 레이어 매핑

각 단계를 핵심 질문 → 전통 SE 개념(ref/260628.md) → 에이전트 오버레이 → 한 줄 인사이트로 매핑한다. S0~S6은 기본 생애주기 단계에 가깝고, S7(비용)·S8(플랫폼/조직)·S9(거버넌스)는 단계라기보다 전 단계에 걸치는 횡단(cross-cutting) 역량·통제면으로 읽는 것이 정확하다.

단계핵심 질문전통 SE 개념에이전트 오버레이인사이트
S0. 의도·문제 정의 왜 이것을 만드는가? Systems Thinking · Product Discovery · Impact Mapping · Wardley Mapping · JTBD Intent Analysis — 모호한 요청을 검증 가능한 목표로 정제 에이전트의 첫 실패는 코드가 아니라 의도 오해에서 온다.
S1. 요구사항·명세 무엇을 해야 하는가? Requirements Engineering · BDD · Specification by Example · Example Mapping · EARS · Acceptance Criteria Spec-Driven Development — 기계가 읽는 명세를 작업 기준으로. Living Documentation 명세가 곧 통제다. vibe coding 대신 명세로 범위·검증 기준을 고정한다.
S2. 도메인·아키텍처 설계 어떤 개념 구조로 풀 것인가? DDD · Event Storming · Clean/Hexagonal · ADR · Threat Modeling · Evolutionary Architecture 설계 규칙·제약을 컨텍스트로 제공(필요 시 MCP로 외부 맥락 연결). BDD가 외부 행동, DDD가 내부 경계 AI가 결정을 빨리 제안할수록 ADR(결정 기록)의 가치가 커진다.
S3. 구현 어떻게 안전하게 만드는가? TDD · Refactoring · SOLID · Pair/Mob · Static Analysis Human+Agent pair · Hooks(결정적 통제) · 권한/제약 레이어 일부 팀 경험상 AI가 mock-heavy 테스트를 선호할 수 있어 state/result 검증 기준을 함께 명시.
S4. 검증·품질 제대로 만들었는가? Test Pyramid · ATDD · Contract Testing · Mutation · Shift-left · Code Review Harness의 Verify 축 · evaluator 게이트 · 계약 기반 검증 강화 구조 검증 통과 ≠ 사실 검증. 자동 게이트는 회귀를 막되 사실을 보증하지 않는다.
S5. 배포·보안 빠르고 안전하게 내보내는가? CI/CD · GitOps · IaC · Progressive Delivery · Feature Flags · DevSecOps Policy-as-Code·Rulesets·branch protection·approvals로 통제, 필요 시 MCP로 외부 맥락 연결 · Push Protection 보안·정책은 배포 전 스캔이 아니라 설계·파이프라인에 내장(shift-left)한다.
S6. 운영·신뢰성 안정적으로 운영 가능한가? SRE · SLI/SLO · Error Budget · Observability · Incident/Postmortem · Chaos · Runbooks Harness의 Observe·복구 레이어 · 운영 피드백 → Spec 폐루프 관측은 측정에서 끝나지 않고 다음 라운드의 명세 입력이 된다.
S7. 비용·지속가능성 지속 가능한가? FinOps · GreenOps · Cloud-native optimization 토큰/credit 사용을 설계 단계로 당겨 비용 의사결정에 반영 비용은 운영에서 드러나지만 설계·배포 선택이 비용 구조를 크게 좌우한다(shift-left).
S8. 플랫폼·조직 확장 조직 규모로 반복 가능한가? Platform Engineering · IDP · Golden Path · Scorecard · Self-service · Team Topologies Agentic DevOps를 제품화 · Golden Path에 agent harness 내장 조직 규모·복잡성이 커질수록 Platform Engineering의 필요성과 효과가 빠르게 커진다.
S9. 거버넌스·폐루프 자율성을 어떻게 통제하는가? Traceability · AI Governance · ADR · DORA Metrics LLMOps · Human-in-the-loop · Control/Observe/Verify 3축 · 운영→Spec 폐루프 실패의 상당수가 명세·통제·검증의 부재에서 오지만, 모델 선택·한계도 중요한 변수다.

6. 에이전트 통제면 (Harness / MCP)

Agentic SDLC를 단발 생성이 아닌 신뢰 가능한 생애주기로 만드는 것은 모델이 아니라 통제면이다. 내부 정리는 이를 6개 레이어(또는 Control·Observe·Verify 3축)로 구조화한다.

레이어역할대응 SDLC 단계
도구 오케스트레이션어떤 도구를 언제 호출할지 조율S3·S4·S5
권한/제약에이전트가 할 수 있는 행동의 경계(allowlist)S5·S9
컨텍스트 관리정책·아키텍처 규칙 주입(MCP), 컨텍스트 분할S1·S2
검증/피드백자동 게이트로 결과 검증, evaluator 판정S4
복구실패 시 롤백·재시도·안전 상태 복원S6
Observability실행 기록·추적으로 내부 상태를 외부에서 관측S6·S9
이 통제면 구조는 본 워크스페이스의 운영 모델(planner 합의 → HA-Han 하네스 게이트 → evaluator 판정 → AR-Ari 기록)과 동형이다. 즉 Agentic SDLC의 통제면은 "검증 가능한 자동 게이트 + 사람 검토 유지"로 구현된다.

7. 도출 인사이트

  1. 하네스부터, 모델도 함께. 에이전트 산출물의 불안정은 상당 부분 명세·통제·검증의 부재에서 오지만, 모델 선택·추론·tool-use 견고성도 큰 축이다 — 둘 다 투자 대상이다.
  2. BDD/DDD만으로 부족 → RE·ADR. 행동 예시(BDD)와 도메인 경계(DDD)만으로는 승인·변경 추적·결정 이유가 자동 해결되지 않는다. 요구공학과 결정 기록이 에이전트 시대에 더 중요해진다.
  3. 테스트를 재설계. 일부 팀 경험상 AI가 mock-heavy(런던식) 테스트를 선호할 수 있다. state/result 중심·계약 기반 검증을 명시적으로 설계한다.
  4. 비용·보안·정책을 shift-left. FinOps·Threat Modeling·Policy-as-Code를 설계·배포로 당긴다. 단 비용은 설계뿐 아니라 사용량·운영 행태·거버넌스에도 강하게 연동된다.
  5. 사람 검토는 자율성의 안전장치. Autopilot이어도 merge/deploy는 repository policy와 human review 게이트를 통과한 뒤에만 가능하다.
  6. 운영→Spec 폐루프가 핵심. 관측 결과가 명세로 되돌아오지 않으면 Agentic SDLC는 단발 자동화에 그친다.
  7. 정답 방법론은 없다. 라이프사이클의 병목을 보고 필요한 층위 개념을 조합한다(아래 7장).

10. 근거·출처

본 문서는 워크스페이스 내부 자료를 기반으로 정리했으며, 외부 공개 출처로 보완했다. 내부 발표·정리 자료(파일명·내부 링크 등 비공개 식별자는 공개 산출물에서 제외)는 BDD → Spec-Driven → CI/CD/GHAS → 운영 피드백 → Agentic DevOps 연결 구조를 공통 제시한다.

  • 외부 공개 참고(개념 출처): Cucumber(BDD: Discovery–Formulation–Automation), Martin Fowler(DDD·Ubiquitous Language·Bounded Context·Microservices), Thoughtworks(Lightweight ADR·Evolutionary Architecture), CNCF Platform Engineering 백서·IDP·Golden Path, FinOps Foundation(비용 shift-left), Microsoft Azure(Agentic DevOps), ISO/IEC/IEEE 12207(SW life cycle).

고유 수치·연도·제품 상태 주장은 외부 공유 전 각 1차 출처로 재확인할 것.

검증 경계

Caveat: 이 문서는 표준 개념과 내부 정리를 종합한 매핑·인사이트 지식 베이스다. 단계 구분(S0–S9)은 설명을 위한 모델이며 배타적·순차적 절차가 아니고, S7·S8·S9는 횡단 역량·통제면에 가깝다. Harness Engineering·Spec-Driven Development·Agentic DevOps는 확립된 학술 표준이 아닌 진행 중인 실무/벤더 프레임이며, MCP는 정책 주입이 아니라 데이터·도구 연결용 개방 표준이다. 개념 정의는 요약이고, 출처별 정확한 정의·연도·최신 상태는 1차 자료로 확인해야 한다. 하네스 PASS는 구조 검증이지 사실 보증이 아니다.
