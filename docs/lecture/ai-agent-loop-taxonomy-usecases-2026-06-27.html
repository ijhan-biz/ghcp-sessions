1. Executive Summary

핵심 판단: 최근 제시되는 agent loop는 크게 단일 agent 반복형, 평가자 포함 개선형, 도구/RAG 연결형, 멀티에이전트 협업형, 운영 게이트형, 장기 자율 실행형, 그리고 최근 부상한 동적 생성·코드 오케스트레이션형(Claude Dynamic Workflows 등)으로 나뉘니다. 토큰량은 루프 이름보다 반복 횟수, 도구 결과 크기, evaluator 수, memory carryover, retry budget에 의해 결정됩니다. 그리고 루프 선택만큼 중요한 것이 루프 엔지니어링입니다 — 종료 조건·컨텍스트·상태·오류·관측을 소프트웨어로 설계해야 실제 production 품질이 됩니다(§7–§9). 그리고 그 루프를 사용자에게 표준 이벤트로 노출하는 인터랙션 계층이 AG-UI입니다(§10).

4. 토큰량 추정 모델

정확한 토큰량은 모델, context window, tool 결과 크기, 숨은 reasoning token 정책, 재시도 횟수에 따라 달라집니다. 따라서 이 보고서는 가격표가 아니라 budgeting heuristic을 제시합니다.

Estimated total tokens per successful task

T_total ≈ T_base_prompt
        + T_context_carryover
        + Σ(loop_step_input + loop_step_output)
        + Σ(tool_result_tokens)
        + Σ(evaluator_or_reviewer_tokens)
        + T_memory_read_write
        + retry_count × T_retry_unit

Main multipliers:
- loop_iterations: ReAct/tool/computer-use 반복 횟수
- evaluator_count: critic, judge, reviewer, red-team 수
- parallel_agents: worker/debate/swarm agent 수
- retrieved_chunks: RAG chunk 수와 chunk 크기
- tool_payload_size: browser/screen/test/log 출력 크기
- retry_budget: 실패 후 재시도 허용 횟수

6. 사용처 추천

짧은 답변·분류

추천: Routing, prompt chaining. 이유: 토큰량이 낮고 실패 지점이 명확합니다. 피함: multi-agent debate.

근거 기반 리서치

추천: Agentic RAG + evaluator-optimizer. 이유: source freshness와 caveat를 함께 관리할 수 있습니다. 피함: source 없는 reflection.

코딩·리팩터링

추천: Plan-and-Execute + autonomous coding + human PR gate. 이유: issue→patch→test→PR 루프가 GitHub-native 검증과 맞습니다.

UI/브라우저 QA

추천: Computer-use/browser loop + strict screenshot cap. 이유: 화면 관찰이 필요합니다. 피함: 권한 높은 production 계정.

전략·아키텍처 비교

추천: Multi-agent debate 또는 orchestrator-workers. 이유: 제품, SRE, 보안, 비용 관점을 나눌 수 있습니다. 주의: 합의가 사실 검증은 아닙니다.

반복 운영 자동화

추천: Graph/state-machine + memory loop + human-in-the-loop. 이유: 상태·재개·감사가 필요합니다. 피함: stop condition 없는 자율 반복.

대규모 fan-out·저컨텍스트 오케스트레이션

추천: Dynamic workflow(코드-오케스트레이터). 이유: 루프·분기·중간결과를 스크립트가 들고 있어 컨텍스트 폭주 없이 수백 subagent로 확장됩니다. 피함: 작은 작업, budget kill-switch·중단 뷰 미비.

Dynamic workflow 보강: Claude Code의 Dynamic Workflows(research preview)는 “Claude가 작성하는 JavaScript 스크립트를 런타임이 백그라운드에서 실행하며 subagent를 스케로 오케스트레이션”하는 패턴입니다. orchestrator-workers를 코드로 옮겨 오케스트레이터 역할을 런타임 스크립트가 맡으므로, 모델 컨텍스트에는 최종 답만 남아 대규모 fan-out에도 컨텍스트가 터지지 않습니다(런당 최대 16 동시·1,000 총 agent). “dynamic”은 스크립트를 Claude가 그때그때 생성한다는 뜻이며, 사람이 고정 DAG를 그리는 것과 다릅니다. 정의·제약·Copilot 구현 경로는 037 문서, 공식 정의는 docs.claude.com/en/docs/claude-code/workflows 참조.
추천 요약: 기본값은 작은 루프입니다. 먼저 routing/prompt chaining/RAG로 시작하고, 실패 비용이 크거나 품질 기준이 명확할 때 evaluator를 추가합니다. 병렬·멀티에이전트·computer-use는 관측성과 budget kill-switch가 준비된 뒤에만 승격합니다.

7. 루프 엔지니어링: 원칙과 설계 고려사항

루프를 고르는 것과 운영 가능하게 만드는 것은 다릅니다. 루프 엔지니어링은 루프의 정의를 넘어 종료 조건·컨텍스트·상태·오류·권한·관측을 소프트웨어로 설계하는 규율입니다. 현장의 production 품질 agent는 “프롬프트 + 도구 한 봉지 + 목표까지 루프”가 아니라 대부분 잘 설계된 소프트웨어이며, LLM 단계가 결정론 코드 사이에 끼워집니다(12-factor agents). 많은 팀이 프레임워크로 70–80%까지 빠르게 도달한 뒤, 그 위를 넘기려면 프롬프트·흐름·컨텍스트를 직접 소유해야 함을 발견합니다.

‘프롬프트하는 나’를 시스템으로 대체하기

루프 엔지니어링의 한 줄 정의는 “매번 프롬프트하며 루프를 돌리던 사람(human-as-loop)을, 그 판단을 코드로 옮긴 시스템(system-as-loop)으로 대체하는 것”입니다. 사람이 손으로 반복하던 판단을 하나씩 시스템 구성요소로 외부화하면, 같은 작업이 재현 가능·관측 가능·확장 가능해집니다.

‘프롬프트하는 나’가 매번 하던 일시스템으로 대체(이 문서의 어디서)
출력을 읽고 다시 프롬프트evaluator·검증 게이트 + 재시도 로직 (§7 오류 압축, §8 eval)
언제 멈출지 눈으로 판단종료 조건: max_steps/tokens/no-progress/done-tool (§7·§8)
무엇을 붙여넣을지 고르기컨텍스트 큐레이션: compaction/JIT/note-taking (§7)
막혔을 때 방향 전환오류 압축 + replan + human gate (§7·§9)
결과가 맞는지 눈으로 확인hard signal 검증: 테스트/PR/재현 (§8)
다음에 또 수동 반복재현 가능한 하네스: launch/pause/resume·체크포인트 (§7·§8)
요지: 위 표의 오른쪽이 갖춰질수록 ‘프롬프트 장인’ 한 명에 의존하지 않고 팀·시스템이 같은 품질을 재현합니다. 즉, 가치는 “더 좋은 프롬프트”가 아니라 “더 좋은 루프”로 이동합니다. (이 프레이밍은 실밤개발자, “루프 엔지니어링 — ‘프롬프트하는 나’를 시스템으로 대체하는 법” 강연에서 가져왔습니다.)

모든 루프의 공통 골격

# 어떤 루프(ReAct·plan-execute·evaluator·…)도 아래 골격의 변형이다 (12-factor agents)
context = [initial_event]                      # 사용자 메시지 / webhook / cron
while True:
    next_step = llm.determine_next_step(context)   # 1) 다음 단계 = 구조화 출력(tool call)
    context.append(next_step)
    if next_step.intent == "done":                 # 4) 종료 판정
        return next_step.final_answer
    result = execute_step(next_step)               # 2) 결정론 코드가 도구 실행
    context.append(result)                         # 3) 결과를 컨텍스트에 추가
핵심: 루프의 이름이 아니라 종료·컨텍스트·상태·오류 처리의 품질이 엔지니어링 난이도를 결정합니다. 좋은 agent는 “도구 한 봉지 주고 끝날 때까지 돌리기”가 아니라 대부분 명시적 제어 흐름입니다.

핵심 원칙 (12-factor agents · Anthropic)

원칙의미안 지키면
흐름을 소유하라 (Own your control flow)분기·중단·재시도·승인 지점을 코드가 소유. LLM에 전권 위임 금지무한 루프, 통제 불가, 분기 폭주
컨텍스트를 소유하라 (Own your context window)컨텍스트는 유한 자원. 매 턴 무엇을 넣을지 큐레이션context rot(길어지면 정확도↓), 비용 폭증
도구는 구조화 출력 (Tools = structured outputs)LLM은 JSON을 내고 결정론 코드가 실행파싱 실패, 비결정성
오류를 압축해 넣어라 (Compact errors)실패를 요약해 다음 턴에 주되 재시도 상한같은 오류 반복, retry storm, 토큰 낭비
상태를 외부화 (Stateless reducer · launch/pause/resume)실행상태=비즈니스상태, 일시정지·재개 가능재현 불가, 장애 복구 불가
작은 초점 agent (Small, focused)한 agent가 모든 걸 하지 않게drift, 평가 불가, 컨텍스트 오염
사람도 도구 호출로 (Human via tool calls)승인·질문도 tool call로 모델링고위험 자동 실행, 의사결정 은폐

설계 고려사항

종료 조건

max_steps, max_tokens, retry_cap, 무진전(no-progress) 감지(같은 tool/plan N회), 명시적 done tool. “언제 멈추는가”가 없으면 production 불가.

컨텍스트 전략(Anthropic)

compaction(요약 후 재시작), 구조적 note-taking(NOTES.md/메모리), just-in-time(파일경로·쿼리 식별자로 런타임 로드), tool-result clearing(과거 raw 결과 제거), sub-agent(깨끗한 컨텍스트·1–2k 토큰 요약 반환).

상태·체크포인트

단계마다 상태 저장 → 중단/재개/롤백. 비가역 action은 체크포인트+승인 뒤에만.

결정성·멱등성

tool은 재시도 안전(idempotent)하게. 외부 effect는 idempotency key로 중복 방지.

권한 경계

read/write/destructive 분리. 고위험은 human gate. 도구 과다(bloated tool set) 금지 — 사람도 못 고르면 LLM도 못 고릅니다.

컨텍스트 예산

“가장 작은 고신호 토큰 집합”을 찾는다. 프롬프트는 right altitude(너무 세부·너무 모호 사이), 예시는 소수의 canonical만.

8. 구현 고려사항: 루프 스켈레톤·예산·관측성

아래는 위 원칙을 코드로 옮긴 production 루프 스켈레톤입니다. 데모 루프와의 차이는 측정·상한·복구·관측이 들어간다는 점입니다.

loop_config = {
  "max_steps": 20, "max_tokens": 200_000, "retry_cap": 2,
  "timeout_s": 900, "fan_out_max": 8, "kill_switch_tokens": 300_000,
  "stop_tools": ["done", "ask_human"], "checkpoint": "every_step"
}

state = load_or_init(run_id)                 # launch / pause / resume
while state.steps < cfg.max_steps and state.tokens < cfg.max_tokens:
    ctx   = curate(context)                  # 컨텍스트 큐레이션: compaction / JIT / tool-result clearing
    step  = llm.next_step(ctx)
    log(trace_id, model_id, prompt_ver, step, state.tokens)   # 관측: 모든 결정 기록
    if step.intent in cfg.stop_tools: break  # 종료 / 사람 호출
    if no_progress(state, step): break       # 무진전 감지(같은 tool/plan 반복)
    try:
        result = execute(step)               # 결정론 실행(idempotent, 권한 검사)
    except ToolError as e:
        result = compact_error(e)            # 오류 압축, retry_cap 적용
    checkpoint(run_id, state)                # 단계별 상태 저장 → 재개/롤백
    context = append_and_maybe_compact(context, step, result)
    state.advance(result)                    # steps++, tokens += result.tokens

예산·상한 파라미터

파라미터역할권장 기본(작업별 조정)
max_steps루프 폭주 차단routing 3 · react 8 · plan-execute 12 · coding 30+
max_tokens / kill_switch_tokens비용 상한p95 예산 · kill = p95 +30~50%
retry_cap재시도 상한1–2 (이후 block·사람)
timeout_s행(hang) 방지작업별(짧은 60 · 긴 900+)
fan_out_max병렬 폭주 방지4–8 (sub-agent/parallel)
no_progress_window무진전 감지같은 tool/plan 3회

도구 계약 설계(Anthropic)

반환은 토큰 효율적으로, 용도는 모호하지 않게 1:1, 오류에 견고, 입력 파라미터는 서술적. 겹치는 도구·과다 도구는 선택 오류를 부릅니다.

관측성(필수)

단계별 trace에 trace_id, step_index, model_id, prompt_version, tool_call+args, retrieved_source, tokens(in/out), latency, decision, retry_count, stop_reason. 관측되지 않는 루프는 배포하지 않는다.

Eval 하네스(루프 지표)

task/verified success, steps-to-done(p50/p95), no-progress rate, recovery-after-error rate, tool-call success, unsupported-claim rate, token/cost per success. golden+adversarial+regression set.

재개·멱등성

체크포인트로 중단 지점부터 재개. 같은 step을 두 번 실행해도 부작용이 한 번만 일어나도록 idempotency key 사용.

9. 프로덕션 성숙도와 준비도 체크리스트

“실제 쓸 수 있는 수준”을 단계로 나눕니다. 대부분의 데모는 L0–L1에 머물고, 고객 대면·고위험 워크로드는 L4가 필요합니다.

레벨이름특징적합
L0Prototypewhile-loop + 도구, 상한 없음, 데모만실험·PoC
L1Guardedmax_steps/tokens/retry, done-tool, 기본 read-only내부 보조 도구
L2Observable단계별 trace, eval set, 토큰 대시보드파일럿
L3Durable체크포인트·재개, 멱등 tool, compaction/note-taking장기·대량 작업
L4Governedhuman gate, 권한 분리, kill-switch, 감사 로그, rollback고위험·고객 대면

Production 승격 체크리스트

루프를 production에 올리기 전:
[ ] 종료 조건(max_steps/tokens/retry/no-progress/done-tool)이 모두 있는가
[ ] 비용 kill-switch와 p95 token 예산이 있는가
[ ] 모든 단계가 trace로 남고 재현 가능한가
[ ] 실패가 요약되어 다음 턴에 들어가고, 무한 재시도가 막히는가
[ ] 컨텍스트 전략(compaction/JIT/sub-agent)이 정의됐는가
[ ] 상태 체크포인트로 중단·재개·롤백이 되는가
[ ] 비가역 action 앞에 human gate가 있는가
[ ] tool이 멱등하고 read/write/destructive가 분리됐는가
[ ] golden/adversarial/regression eval이 있는가
루프 고유 안티패턴: ① “loop until done” 맹신(종료·예산 없이 목표까지 돌림) → 폭주·비용 사고. ② context dumping(모든 결과를 그대로 누적) → context rot. ③ retry storm(압축·상한 없는 재시도). ④ 공유 없는 멀티에이전트(서브가 맥락을 나눠 받지 못해 충돌) — 가능하면 단일 스레드 선형 루프를 먼저 고려. ⑤ evaluator theater(기준 없는 자기평가로 “개선” 주장). ⑥ 관측 없는 배포(재현 불가).

10. AG-UI: 루프를 UI에 연결하기 (Agent–User Interaction Protocol)

루프는 결국 사용자에게 보여지고, 조종되고, 승인되어야 합니다. AG-UI(Agent–User Interaction Protocol)는 agent 백엔드와 사용자 대면 앱을 잇는 open·lightweight·event-based 표준입니다(ag-ui-protocol, MIT, CopilotKit 발). §7–§9가 루프를 운영 가능하게 만든다면, AG-UI는 그 루프를 사용자 대면 product로 만드는 인터랙션 계층입니다.

agentic 프로토콜 스택에서의 위치

계층프로토콜역할
Agent ↔ Tools/DataMCP (Model Context Protocol)에이전트에 도구·데이터 연결(Anthropic 발)
Agent ↔ AgentA2A (Agent to Agent)에이전트 간 협업·작업 분배(Google 발)
Agent ↔ UserAG-UI (Agent–User Interaction)에이전트를 사용자 대면 앱에 연결(이벤트 기반)
왜 필요한가: agent는 장기 실행·스트리밍·비결정적·구조화+비구조화 IO 혼합·재귀적 구성이라 전통적 REST/GraphQL 요청-응답 모델을 깨뜨립니다. AG-UI는 HTTP/WebSocket 위에서 이 간극을 메우는 추상화 계층입니다.

동작: 루프가 이벤트를 emit한다

루프 실행 중 백엔드가 약 16개 표준 이벤트를 emit하고, 프런트엔드가 구독합니다. 전송은 SSE·WebSocket·webhook 무관이며 loose format matching과 reference HTTP 구현·기본 connector를 제공합니다. §8의 log(...) 지점이 사실상 AG-UI 이벤트 발행 지점이 됩니다.

이벤트 카테고리대표 이벤트루프 연결(§7–§9)
LifecycleRUN_STARTED/FINISHED/ERROR, STEP_STARTED/FINISHED루프 시작·종료·단계 경계, stop_reason
Text messageTEXT_MESSAGE_START/CONTENT/END토큰 스트리밍 출력
Tool callTOOL_CALL_START/ARGS/END, TOOL_CALL_RESULT도구 호출·결과 스트리밍(tools=structured outputs)
StateSTATE_SNAPSHOT, STATE_DELTA(JSON Patch), MESSAGES_SNAPSHOT양방향 상태 동기화·체크포인트
SpecialRAW, CUSTOM스펙 미커버 데이터·확장
주의: 정확한 이벤트 이름·개수는 스펙 버전에 따라 달라질 수 있으므로 도입 시 공식 이벤트 문서를 확인하세요.

루프 엔지니어링과 매핑되는 빌딩블록

스트리밍 채팅

토큰·이벤트 실시간 스트리밍, cancel/resume. §8의 timeout·중단과 연결.

양방향 shared state

read-only/read-write 타입드 스토어, event-sourced diff(STATE_DELTA)·충돌 해소. §8 checkpoint를 UI와 공유.

Generative UI

모델 출력을 안정적·타입드 컴포넌트(static/declarative)로 렌더. 자유 텍스트 대신 통제된 UI.

Thinking steps

trace·tool 이벤트에서 중간 추론을 시각화(raw chain-of-thought는 노출 안 함). §8 관측 trace의 사용자 버전.

HITL interrupts

흐름 중 pause·approve·edit·retry·escalate를 상태 손실 없이. §7 “사람도 도구 호출로”의 표준 구현.

Sub-agent·steering

scoped state·tracing·cancellation의 중첩 위임, 실시간 agent steering으로 실행 방향 재지정.

설계 고려사항

이벤트를 1급 시민으로

관측 로그를 사후에 붙이지 말고, 루프 단계마다 이벤트를 발행하도록 설계. §8 trace 필드가 그대로 이벤트 payload가 된다.

스냅샷보다 델타

매 턴 전체 상태 대신 STATE_DELTA(JSON Patch)로 동기화해 지연·대역폭을 줄인다. read-write엔 충돌 해소 규칙 필수.

raw CoT 비노출

thinking steps는 trace·tool 이벤트에서 구성하고 원시 사고사슬은 내보내지 않는다(안전·일관성).

전송 독립·중단 가능

SSE/WebSocket/webhook 무관, cancel/resume 토큰으로 §8 체크포인트와 연결해 중단·재개를 UI에서 제어.

연결 요약: AG-UI는 §8의 관측·trace를 표준 이벤트로, §7의 human-via-tool-calls를 interrupts로, sub-agent를 scoped composition으로, checkpoint/resume를 cancel/resume으로 매핑합니다. 즉 루프 엔지니어링 산출물을 그대로 사용자 인터페이스에 연결하는 표준입니다. LangGraph·CrewAI·Microsoft Agent Framework·Google ADK·AWS Strands/Bedrock AgentCore·Pydantic AI 등이 지원합니다.
