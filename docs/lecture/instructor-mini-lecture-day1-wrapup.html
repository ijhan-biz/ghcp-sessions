안티패턴

“알아서 잘 해줘.”

무엇이 완료인지, 무엇을 바꾸면 안 되는지, 어떻게 확인할지 모두 모델에게 떠넘긴다.

좋은 지시

R · 역할누구로 일하는가
C · 맥락무엇을 알고 시작하는가
T · 작업무엇을 바꾸는가
C · 제약무엇을 넘지 않는가
V · 검증어떻게 통과를 확인하는가
O · 출력어떤 형태로 끝나는가

R/C/T/C/V/O는 프롬프트를 길게 만드는 형식이 아니라 완료의 경계를 먼저 고정하는 장치다.

02 · Acceptance Criteria

05 / 10

AC는 정상·예외·경계로 나눠 쓴다

구분완료 기준검증 예시판정
정상일반 상품에는 세율 10%를 적용한다.tax(1000) === 100PASS / FAIL
예외면세 상품에는 세금 0을 반환한다.tax(1000, true) === 0PASS / FAIL
경계음수 금액 입력은 오류로 거부한다.tax(-1) throwsPASS / FAIL
AC가 없다는 것은 완료 판정을 모델에게 맡긴 것이다. 결국 시킬 일을 사람이 덜 검증한 셈이다.
Happy path만 쓰면 실제 경계는 모델이 추측한다05

02 · Measurable evidence

06 / 10

측정할 수 없는 문장은 AC가 아니다

AC마다 검증 수단을 붙인다

  • 동작은 자동 테스트로 확인한다.npm test
  • 구조는 lint와 schema로 확인한다.npm run lint
  • 금지 조건은 policy와 check 스크립트로 확인한다.npm run policy-check

느낌 기준은 분리한다

“빠르다.”
“직관적이다.”

측정 방법과 임계값이 없다면 자동 판정할 수 없다. 지금 검증하지 않을 품질 기대라면 non-goal로 명시한다.

Non-goal
이번 변경에서는 주관적 사용성 개선을 완료 조건으로 삼지 않는다.
기준 + 명령 + 측정값 = 판정 가능한 AC06

03 · Choose the actor first

07 / 10

모델을 고르기 전에 주체부터 고른다

HUMAN

사람이 맡을 일

  • 목표와 완료 기준 결정
  • 변경 승인과 책임
  • 조직 정책·위험 판단
TOOL · NO MODEL

  • 환경 점검과 checkpoint
  • 명령·테스트·gate 실행
  • 동일 입력의 pass/fail 판정
AI ASSISTED

모델이 보조할 일

  • 짧은 다음 행동 제안
  • 작은 구현과 샌드박스 검증
  • 경계·예외·허용 범위 구조화
모든 활동에 모델이 필요한 것은 아니다. 책임과 결정론이 필요한 곳에서는 사람과 도구가 먼저다.

03 · Evidence over price tags

08 / 10

모델 선택 근거는 가격표가 아니라 반복 통과 기록이다

  1. 활동의 성격을 고정한다제안·구현·구조화처럼 실제 과업 단위로 비교한다.
  2. 동일한 품질 게이트를 적용한다정확성·경계 처리·허용 범위·실행 검사를 같은 조건으로 본다.
  3. 여러 번 재현되는지 확인한다한 번의 좋은 답이 아니라 반복 통과 여부를 기록한다.
  4. 당일 운영 조건으로 최종 결정한다조직 정책·사용 가능 모델·세션 로그를 마지막에 대조한다.

선택 질문

“이 활동의 품질 게이트를 반복해서 통과했는가?”

속도와 요금은 품질 하한을 통과한 후보끼리 비교할 때 의미가 있다.

활동 적합성 → 품질 재현 → 정책·로그 확인08

Closing principle

10 / 10

실패를 게이트로 고정할수록 하네스가 단단해진다

01Baseline재현 가능한 시작점
02실행통제된 도구와 범위
03실패 관측로그·diff·trace 수집
04Gate 고정다음에는 자동으로 차단
05재실행같은 명령으로 재판정

원하는 결과와 완료 기준을 사람이 먼저 정하고, 그 일에 맞는 주체·모델을 고른 뒤, 재실행 가능하고 결정론적인 하네스로 검증까지 남긴다.

무엇 → AC → 주체·모델 → 하네스 → 증거

하네스가 약하면 PASS가 잘못된 안심을 준다. 한 번에 완성하려 하지 말고, 실패와 판단 이력을 다음 실행의 가드레일로 바꾼다.
