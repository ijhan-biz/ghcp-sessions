1. 개념 정리 — 무엇을 "실 사례"로 보는가

Agentic SDLC는 라이프사이클의 각 단계를 사람이 직접 하는 대신, 명세(spec)를 받아 에이전트가 탐색·구현·검증하고 사람은 방향 설정·검토·승인을 맡는 개발 생애주기다. 핵심 전제는 ① 명세 우선(Spec-Driven) ② 통제면 우선(Harness over Prompt) ③ 사람 검토 유지(Human-in-the-loop) ④ 폐루프(운영 피드백이 명세로 환류)다.

Harness Engineering은 "AI가 파일을 바꾸고 명령을 실행하는 흐름을 관찰 가능하고 통제 가능한 실행 환경으로 만드는 일"이다. 결과 품질은 좋은 프롬프트보다 아래 통제면의 설계가 좌우한다. 이 문서는 각 사례를 이 7개 통제면에 매핑한다.

명세/컨텍스트→ 권한 게이트→ 실행 격리→ 검증 게이트→ 관측/감사→ 복구/롤백→ 학습 환류
통제면질문대표 구현물(파일/메커니즘)

권한 게이트어떤 도구를 언제 승인 없이/승인 후 쓰나?allow/deny 목록, approval policy, tool allowlist
실행 격리변경/실행은 어디서 일어나나?ephemeral runner, Docker, git worktree, sandbox
검증 게이트결과가 좋은지 무엇으로 판정하나?lint/test/보안스캔 hook, 리뷰 서브에이전트, eval
관측/감사무엇을 했는지 어떻게 남기나?trace/EventStream, git commit, session log
복구/롤백실패하면 어떻게 되돌리나?edit auto-revert, checkpoint resume, PR 미머지

읽는 법. 각 사례의 정량 성과(배수·%·해결률)는 발표·저자·논문의 자가 보고다. 표본·측정법이 공개되지 않은 경우가 많으므로 일반 법칙이 아니라 방향성 신호로 읽고 자사 환경에서 별도 검증한다. Harness "PASS"는 구조 검증이지 사실 검증이 아니다.

CASE A1 · 공식 코드

GitHub Copilot cloud agent — 이슈 배정 → ephemeral runner → PR

클라우드 에이전트GitHub Actions 격리MCPPR 게이트

📦 공개 저장소: github/awesome-copilot (공식 인스트럭션·프롬프트 큐레이션) · agentsmd/agents.md (AGENTS.md 표준, 이전 openai/agents.md에서 이동) — 코딩 에이전트 코어는 비공개

개요. GitHub Issue를 @copilot에 배정하면(또는 Chat·API·CLI·MCP·Jira/Slack/Teams 등에서 시작) Copilot이 일회용 GitHub Actions 러너(Ubuntu/Windows, 최대 59분)를 띄워 리포를 탐색하고 계획을 세운 뒤 새 브랜치에 코드를 바꾸고 린트·테스트를 돌린 다음 Pull Request를 연다. 사람은 PR에서 리뷰·수정·머지한다. "AI가 SDLC를 대체"가 아니라 GitHub의 기록(Issues/PR/Actions/Audit) 위에서 에이전트가 후보를 만들고 사람이 승인하는 폐루프다.

Agentic SDLC 매핑

Issue(명세)→setup steps→ plan+구현(branch)→lint/test·code review→ PR→사람 리뷰·머지

하네스 ① 컨텍스트 — 커스텀 인스트럭션

리포 전역 규칙은 .github/copilot-instructions.md, 경로별 규칙은 .github/instructions/NAME.instructions.md(frontmatter의 applyTo glob), 에이전트 규칙은 트리 어디서나 AGENTS.md(가장 가까운 파일 우선)로 둔다.

# .github/copilot-instructions.md
## Repository Summary
TypeScript/Node.js REST API. Express 5.x, Node 20 LTS, Vitest, ESLint.

## Build and Validate
- Always run `npm install` before building.
- Build: `npm run build` (outputs to dist/)
- Test: `npm test` — run before every commit.
- Lint: `npm run lint` — must pass with zero errors.
- Order: install -> build -> test -> lint.

## Project Layout
- src/routes/ Express handlers · src/models/ Prisma models
- prisma/schema.prisma DB schema · dist/ compiled (do not edit)

## Coding Standards
- async/await only (no raw .then()). Explicit error handling in every handler.
- Never hardcode secrets; use process.env with a .env.example.
- Trust these instructions; search the codebase only if something seems missing.
---
applyTo: "src/payments/**/*.ts"
excludeAgent: "code-review"
---
## Payments Module Rules
- Use `make test-payments` instead of `npm test` in this directory.
- All payment amounts must use integer cents (never floats).

하네스 ② 실행 격리 — 에이전트 환경 사전설치

에이전트가 일할 환경은 .github/workflows/copilot-setup-steps.yml로 미리 준비한다. job 이름이 반드시 copilot-setup-steps여야 Copilot이 인식한다. 방화벽은 기본 ON, timeout-minutes 최대 59.

name: "Copilot Setup Steps"
on:
  workflow_dispatch:
  push:
    paths: [ .github/workflows/copilot-setup-steps.yml ]
  pull_request:
    paths: [ .github/workflows/copilot-setup-steps.yml ]

jobs:
  # 이 이름이 아니면 Copilot이 픽업하지 않는다.
  copilot-setup-steps:
    runs-on: ubuntu-latest
    permissions:
      contents: read          # 최소 권한. 에이전트 토큰은 별도.
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: "npm"
      - run: npm ci             # 의존성 사전 설치

honored 필드는 steps · permissions · runs-on · services · snapshot · timeout-minutes뿐. 어떤 setup step이 실패(비영 종료)하면 나머지를 건너뛰고 현재 상태로 작업을 시작한다.

하네스 ③ 권한 게이트 — MCP 도구 허용목록

MCP는 리포 Settings → Copilot → MCP servers의 JSON으로 설정한다. tools에 읽기 전용 도구만 허용목록으로 두는 게 권장인데, 이유는 아래 경고 때문이다.

{
  "mcpServers": {
    "sentry": {
      "type": "local",
      "command": "npx",
      "args": ["@sentry/mcp-server@latest", "--host=$SENTRY_HOST"],
      "env": {
        "SENTRY_HOST": "https://contoso.sentry.io",
        "SENTRY_ACCESS_TOKEN": "$COPILOT_MCP_SENTRY_ACCESS_TOKEN"
      },
      "tools": ["list_issues", "get_issue"]  ← 읽기 전용만 허용
    }
  }
}
공식 경고. "Once you have configured an MCP server, Copilot will be able to use the tools provided by the server autonomously, and will not ask for your approval before using them." → 그래서 쓰기/파괴 도구는 허용목록에서 뺀다. GitHub·Playwright MCP는 기본 활성.

하네스 ④ 사람 게이트 · 관측

  • 권한 경계: branch protection ruleset, Copilot을 bypass actor로 추가할지 여부, PR 리뷰 없이는 머지 불가.
  • Actions 게이트: 에이전트가 만든 워크플로 실행은 "Approve and run workflows" 버튼을 사람이 눌러야 시작.
  • 관측: github.com Agents 탭의 session 로그로 무엇을 했는지 추적. 보안 스캔 + Copilot code review가 기본 검증.

팀 하네스 맥락 · 결과 · 에피소드

  • 맥락: 코드네임 "Project Padawan"(2025-02 공개). 클라우드 컴퓨트로 "유일한 답은 GitHub Actions"를 택함(평일마다 4천만+ 잡 실행 생태계 재사용). 에이전트는 자기가 만든 브랜치에만 push, 인터넷은 허용 목록으로 제한.
  • 결과: coding agent는 2025-05 Enterprise·Pro+ GA. (자가보고) 통제실험서 Copilot 사용 개발자가 JS 과제를 55% 빠르게 완료(95명, 1h11m vs 2h41m).
  • 에피소드: "PR을 열게 한 개발자는 그 PR을 승인할 수 없다" — 자기승인 금지·branch protection을 기본 정책으로 못박음(사람은 자기 제출물을 제대로 리뷰 못 한다는 통찰). 내부적으로도 Copilot+Cursor+Claude+Codex 혼용 현실을 인정.

💰 토큰 절약 포인트: 커스텀 인스트럭션 선주입으로 탐색 토큰을 아낀다. .github/copilot-instructions.md·AGENTS.md에 빌드·테스트·레이아웃 규칙을 미리 적어 두고 "이 지침을 신뢰하고 꼭 필요할 때만 코드베이스를 탐색하라"고 명시하면, 에이전트가 매번 파일을 뒤지며 컨텍스트를 채우는 반복 tool 호출이 사라진다. 또 초기 탐색은 RAG(GitHub 코드검색)로 처리해 저장소 전체를 컨텍스트에 넣는 대신 질의와 관련된 코드 조각만 가져온다 — "전체 덤프" 대신 "관련 부분만"이 토큰 절감의 핵심. 실행 격리(ephemeral runner)라 세션이 끝나면 컨텍스트가 리셋되어 누적 팽창도 없다.

하네스 ③ 결정론적 게이트 — hooks (PreToolUse / PostToolUse)

이벤트별(PreToolUse, PostToolUse, SessionStart, Stop, PreCompact 등) 셸 명령을 matcher로 도구에 걸어 실행. PreToolUse는 permissionDecision:"deny" 또는 exit 2로 액션을 차단하고, PostToolUse는 포맷·린트 같은 사후 검증을 확정적으로 돌린다.

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)", "Bash(npm ci)"],
    "deny":  ["Bash(curl *)", "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
  },
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command",
          "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write 2>/dev/null || true" }]}
    ],
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "if": "Bash(rm *)",
          "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-rm.sh" }]}
    ]
  },
  "env": { "CLAUDE_CODE_ENABLE_TELEMETRY": "1", "OTEL_METRICS_EXPORTER": "otlp" }
}

파괴 명령 차단 훅 — stdin으로 받은 JSON을 검사해 deny 결정을 반환:

#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')
if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{ hookSpecificOutput: {
    hookEventName: "PreToolUse",
    permissionDecision: "deny",
    permissionDecisionReason: "Destructive rm -rf blocked by project policy" }}'
else
  exit 0   # 결정 없음 → 정상 권한 흐름
fi

📦 공개 저장소: SWE-agent/SWE-agent · SWE-agent/mini-swe-agent

개요. Princeton의 SWE-agent(arXiv:2405.15793)는 "같은 LM이라도 인터페이스 설계가 소프트웨어 작업 성능을 좌우한다"는 걸 보인 대표 연구다. 사람에게 HCI가 있듯 LM에게는 ACI(Agent-Computer Interface)가 필요하다. 날것의 셸은 노이즈가 많고 되돌리기 어려운 실수를 유발하므로, ACI는 ① 행동 공간을 잘 정의된 도구로 제약 ② 윈도우드 뷰·린트·state JSON으로 구조화된 피드백 ③ 검증 게이트(편집 시 린트) ④ CURRENT_FILE/LINE/WINDOW로 상태 유지를 한다. 이 모든 게 단일 .yaml로 구동된다.

성과(논문 Table 1 · SWE-bench full). RAG 베이스라인은 GPT-4 Turbo ~1.31% · Claude 3 Opus ~3.79%인데, SWE-agent가 GPT-4 Turbo에서 ~12.47%(Lite 18%), Claude 3 Opus에서 ~10.46%(Lite 13%)로 향상. 논문은 이 격차의 상당 부분을 모델이 아니라 ACI 설계로 귀속한다. 검증 arXiv:2405.15793 Table 1 대조 완료.

검증 게이트 — edit 시 flake8, 깨지면 자동 롤백

ACI의 백미. 파이썬 파일을 편집하면 flake8을 돌려 새 문법 오류가 생기면 편집을 적용하지 않고 원본을 복구하며, 에이전트에게 "적용했다면 이랬을 버전"과 "원본"을 모두 보여준다. 파괴적 커밋을 막는 사전 검사다.

# @yaml signature: edit <start_line>:<end_line> \n <replacement> \n end_of_edit
# docstring: Python files are syntax-checked after edit. On error the edit is NOT applied.
edit() {
    local linter_cmd="flake8 --isolated --select=F821,F822,F831,E111,E112,E113,E999,E902"
    local linter_before_edit=$($linter_cmd "$CURRENT_FILE" 2>&1)
    # ... apply replacement ...
    if [[ $CURRENT_FILE == *.py ]]; then
        _lint_output=$($linter_cmd "$CURRENT_FILE" 2>&1)
        lint_output=$(_split_string "$_lint_output" "$linter_before_edit" ...)
    fi
    if [ -z "$lint_output" ]; then
        export CURRENT_LINE=$start_line; _constrain_line; _print
        echo "File updated. Please review the changes..."
    else
        echo "Your proposed edit has introduced new syntax error(s)..."
        echo "ERRORS:"; echo "$lint_output"
        cp "/root/$(basename "$CURRENT_FILE")_backup" "$CURRENT_FILE"   # 원본 복구
        echo "Your changes have NOT been applied. Please fix and try again."
    fi
}

개요. Aider는 컨텍스트(repo map)와 검증(lint/test reflection)과 관측(auto-commit)을 코드로 붙인 CLI 페어프로그래머다. 핵심 하네스 3개가 모두 원본 파일에서 확인된다.

하네스 ① 컨텍스트 — tree-sitter + PageRank repo map

모든 파일을 tree-sitter로 파싱해 정의(def)/참조(ref) 태그를 뽑고, "A가 B에 정의된 심볼을 참조" 간선의 MultiDiGraph를 만든 뒤 PageRank(personalization)로 중요한 심볼만 골라 토큰 예산(기본 1024)에 맞춰 이진 탐색으로 채운다. 채팅에 올린 파일은 가중치를 크게 부스트.

import networkx as nx
G = nx.MultiDiGraph()                      # 노드=파일, 간선=심볼 참조
for ident in idents:
    mul = 1.0
    if ident in mentioned_idents:            mul *= 10    # 대화에 언급되면 부스트
    if ident.startswith("_"):                mul *= 0.1   # private 강등
    if len(defines[ident]) > 5:              mul *= 0.1   # 너무 흔하면 강등
    for referencer in references[ident]:
        use_mul = 50 if referencer in chat_rel_fnames else 1  # 채팅 파일 대부스트
        for definer in defines[ident]:
            G.add_edge(referencer, definer, weight=num_refs*use_mul, ident=ident)
# 이후 PageRank(personalization=100/num_nodes for chat files) -> 토큰예산 이진탐색

하네스 ② 검증 게이트 — lint/test → reflection(최대 3회)

편집·auto-commit 후 린트/테스트를 돌려 실패 출력을 reflected_message로 LLM에 되먹여 재편집시킨다. 무한루프를 막는 max_reflections = 3 상한이 하드코딩돼 있다.

def run_one(self, user_message, preproc):
    message = user_message
    while message:
        self.reflected_message = None
        list(self.send_message(message))         # 편집 -> auto-lint/test
        if not self.reflected_message:
            break
        if self.num_reflections >= self.max_reflections:   # = 3
            self.io.tool_warning("Only 3 reflections allowed, stopping.")
            return
        self.num_reflections += 1
        message = self.reflected_message          # lint/test 에러를 다시 LLM에게
def flake8_lint(self, rel_fname):
    fatal = "E9,F821,F823,F831,F406,F407,F701,F702,F704,F706"
    cmd = [sys.executable, "-m", "flake8",
           f"--select={fatal}", "--show-source", "--isolated", rel_fname]
    result = subprocess.run(cmd, capture_output=True, text=True, cwd=self.root)
    errors = result.stdout + result.stderr
    return self.errors_to_lint_result(rel_fname, errors) if errors else None

하네스 ③ 관측/복구 — auto-commit(감사추적)

모든 AI 편집은 LLM이 생성한 메시지로 git 커밋된다(기본은 커밋 author를 Name (aider)로 표기, --attribute-co-authored-by 지정 시 Co-authored-by: aider 트레일러 추가) → 되돌리기·감사가 커밋 단위로 가능. 편집 전 dirty 파일은 먼저 dirty_commit()으로 깨끗한 베이스라인을 만든다.

## .aider.conf.yml
model: anthropic/claude-sonnet-4-5-20250929
## Repo map (컨텍스트)
map-tokens: 2048
map-refresh: auto
## Git (관측/복구)
auto-commits: true
dirty-commits: true
attribute-co-authored-by: true
## Lint & Test (검증 게이트)
auto-lint: true
lint-cmd:
  - "python: flake8 --select=E,W,F --max-line-length=120"
auto-test: true
test-cmd: "pytest -x --tb=short"
## 항상 읽는 read-only 컨텍스트
read:
  - CONVENTIONS.md

--read CONVENTIONS.md는 파일을 수정 불가(read-only)로 고정하고 프롬프트 캐싱까지 켠다 — 팀 규칙을 항상 켜 두는 값싼 방법.

팀 하네스 맥락 · 결과 · 에피소드

  • 맥락: 단독 메인테이너 Paul Gauthier가 aider로 aider를 만듦(궁극의 dogfooding). repo map은 tree-sitter AST + PageRank식 그래프 랭킹으로 토큰 예산에 맞춰 저장소 전체의 압축 지도를 LLM에 제공.
  • 결과: (자가보고, git blame) 릴리스마다 새 코드의 70~80%를 aider가 작성(v0.82.0 92%, v0.86.0 88%). 2024-05 SWE-bench Lite 26.3% pass@1 SOTA(당시), lint·test 타당성 게이트 + 6회 재시도.
  • 에피소드: repo map은 구체적 실패에서 탄생 — "print를 전부 BarLog로 바꿔"라면 Foo 클래스와 BarLog 사용법을 함께 봐야 함. 구 ctags 방식은 사용자가 universal-ctags를 수동 설치하는 마찰로 폐기. 약한 모델은 "repo map을 편집 가능한 소스로 착각"해 기본 비활성.

💰 토큰 절약 포인트: 저장소 전체를 토큰 예산에 맞춰 압축하는 게 repo map의 본질이다. tree-sitter로 뽑은 심볼 그래프에 PageRank를 걸어 중요한 정의/참조만 고르고, 토큰 예산(기본 1024~2048)에 맞을 때까지 이진 탐색으로 넣고 뺀다 — 대형 코드베이스를 통째로 주입하지 않고 "가장 관련 있는 심볼 지도"만 준다. --read CONVENTIONS.md 같은 read-only 파일은 프롬프트 캐싱으로 반복 청구를 줄인다. 약한 모델은 map을 편집 대상으로 착각하므로 기본 비활성해 불필요한 큰 컨텍스트와 오작동 재시도를 함께 없앤다.

/speckit.specify        # 기능 설명 -> 구조화된 PRD(spec.md). feature 번호·git 브랜치 자동 생성
/speckit.clarify        # 미명세 영역 질의·해소 (plan 전 권장)
/speckit.plan           # spec + 헌법 제약 -> 기술 아키텍처(data-model, contracts, research)
/speckit.tasks          # plan -> 실행 가능한 tasks.md. 독립 작업은 [P] 병렬 표시
/speckit.analyze        # 산출물 간 일관성·커버리지 교차 분석
/speckit.checklist      # 요구사항 완결성·명확성·일관성 검증용 커스텀 체크리스트 생성
/speckit.implement      # tasks.md 전체 실행
/speckit.converge       # 코드베이스를 spec/plan/tasks와 대조해 남은 작업을 새 task로 추가
/speckit.taskstoissues  # 작업 목록 -> GitHub Issues 로 변환(프로젝트관리 층과 연결)

생성되는 구조 = 폐루프의 기록물

my-project/
├── .specify/
│   ├── templates/              # SDD 커맨드 템플릿(오버라이드/preset/extension 우선순위 스택)
│   └── scripts/{bash,powershell}/
└── specs/
    └── 003-chat-system/        # /speckit.specify 가 만든 자동 번호 브랜치
        ├── spec.md             # user story·acceptance criteria
        ├── plan.md             # /speckit.plan
        ├── research.md         # (자동) 라이브러리 비교 등
        ├── data-model.md
        ├── contracts/          # API/이벤트 계약
        └── tasks.md            # [P] 병렬 마커 포함 실행 목록

Agentic SDLC 매핑. 헌법=거버넌스, spec=요구사항 기록, plan=설계, tasks=작업분해, implement=구현, taskstoissues=프로젝트관리 환류. spec을 git에 버전드로 남겨 명세가 단일 기준(system of record)이 된다. 조직은 extension/preset으로 컴플라이언스 게이트·도메인 용어를 얹는다.

  • 에피소드: spec-driven.md의 시간 비교 — 전통 방식 문서화 ~12시간 vs SDD 커맨드로 15분에 명세+계획 완성. (참고: GitHub 엔지니어링 블로그 URL은 조사 시점 미발견 — 저장소·docs가 1차 근거.)

개요. Jesse Vincent의 obra/superpowers는 Claude Code 등에 합성 가능한 스킬(SKILL.md) + 세션 시작 부트스트랩을 심어, 브레인스토밍·계획·TDD·리뷰를 "제안이 아니라 필수 워크플로우"로 강제한다. 코딩을 시작하기도 전에 "정말 뭘 만들려는 거냐"를 먼저 묻게 만든다.

스킬 구조 & HARD-GATE

각 스킬은 skills/<name>/SKILL.md 디렉터리. frontmatter의 description이 활성화 판단 근거이고, 본문에 강한 게이트를 박는다.

---
name: brainstorming
description: "You MUST use this before any creative work - creating features,
  building components, adding functionality, or modifying behavior.
  Explores user intent, requirements and design before implementation."
---
<HARD-GATE>
Do NOT invoke any implementation skill, write any code, scaffold any project,
or take any implementation action until you have presented a design and the
user has approved it. This applies to EVERY project regardless of simplicity.
</HARD-GATE>

세션 시작 부트스트랩 = 하네스 부착점

<session-start-hook><EXTREMELY_IMPORTANT>
You have Superpowers.
**RIGHT NOW, go read**: @~/.claude/plugins/.../skills/getting-started/SKILL.md
</EXTREMELY_IMPORTANT></session-start-hook>

부트스트랩이 가르치는 3가지: ① 너에겐 스킬이 있다 ② 어떤 작업 전에도 스킬을 먼저 검색하라 ③ 할 수 있는 스킬이 있으면 반드시 써라.

핵심 7단계 & 계획 템플릿

brainstorming → using-git-worktrees(격리) → writing-plans → subagent-driven-development(작업당 새 서브에이전트+2단계 리뷰) → test-driven-development(RED→GREEN→REFACTOR, 테스트 전에 쓴 코드는 삭제) → requesting-code-review → finishing-a-development-branch. 계획의 각 태스크는 정확한 파일 경로·완성 코드·검증 단계를 강제한다.

### Task N: [Component Name]
**Files:**
- Create: `exact/path/to/file.py`
- Test:   `tests/exact/path/to/test.py`
- [ ] Step 1: Write the failing test
- [ ] Step 2: Run test to verify it FAILS ("function not defined")
- [ ] Step 3: Write minimal implementation
- [ ] Step 4: Run test to verify it PASSES
- [ ] Step 5: Commit (git add ...; git commit -m "feat: ...")

서브에이전트는 역할별로 가장 약한(값싼) 모델을 명시하도록 강제한다("모델을 생략하면 세션의 비싼 모델을 상속해 이 절을 무력화한다"). writing-skills 메타스킬로 하네스가 스스로 확장되며, 새 스킬은 적대적 서브에이전트로 검증된다("하네스에 대한 TDD").

팀 하네스 맥락 · 결과 · 에피소드

  • 결과: (자가보고) "에이전트가 계획 이탈 없이 2시간씩 자율 작업하는 게 드물지 않다." 2026년엔 Superpowers 전담 채용까지 확장.

💰 토큰 절약 포인트: 격리 + 값싼 모델 + TDD 세 축으로 토큰을 아낀다. 작업마다 새 서브에이전트를 띄워 탐색·구현 컨텍스트를 본 세션과 분리하고(결과 요약만 회수), 스킬은 온디맨드로만 로드한다. 서브에이전트 정의에는 "가장 값싼(약한) 모델을 명시하라"를 강제해("생략하면 세션의 비싼 모델을 상속해 이 절을 무력화") 리뷰·리서치 같은 반복 작업의 단가를 낮춘다. TDD(RED→GREEN→REFACTOR, 테스트 전 코드는 삭제)로 잘못된 구현을 조기에 걸러 재작업에 쓰는 토큰을 줄인다.

CASE D1 · 엔지니어링 블로그

Anthropic 멀티에이전트 리서치 — orchestrator-worker

📦 공개 저장소: anthropics/claude-cookbooks (이전 anthropic-cookbook에서 이동, 공개 프롬프트·패턴) — 리서치 시스템 자체는 비공개

개요(찬성 진영). Anthropic Research는 lead 에이전트(Claude Opus 4)가 전략을 세우고 병렬 서브에이전트(Claude Sonnet 4)를 스폰해 각자 독립 컨텍스트 창에서 다른 측면을 동시에 탐색·필터링한 뒤 결과를 lead가 종합하는 구조. 내부 리서치 eval에서 단일 Opus 4 대비 +90.2%. 폭넓은 탐색·병렬화가 유리한 리서치형 과제에 맞는 하네스다.

핵심 경제학. 에이전트는 챗 대비 ~4배, 멀티에이전트는 ~15배 토큰을 쓴다. 그런데 BrowseComp에서 토큰 사용량만으로 성능 분산의 80%가 설명된다(나머지는 도구 호출 수·모델 선택). 즉 병렬 서브에이전트는 "토큰을 병렬로 더 쓰는" 유효한 방법. 검증 필요 자가 보고 eval.

오케스트레이션 하네스 = 위임 프롬프트 엔지니어링

블로그의 8개 교훈 중 하네스 설계에 직접적인 것들:

  • 위임을 가르쳐라: 각 서브에이전트에 목표·출력 형식·도구/소스 가이드·명확한 경계를 줘야 한다. "반도체 부족을 조사하라" 같은 모호한 지시는 중복 작업·누락을 부른다.

개요. MAF(agent-framework / Microsoft.Agents.AI)는 Microsoft의 통합 에이전트 프레임워크다. 하네스가 middleware 체인으로 명시적으로 설계돼 있다: ① Agent middleware(전체 run 인터셉트) ② Function middleware(모든 tool 호출 게이트) ③ Chat middleware(LLM 호출 감사). 여기에 선언적 HITL 승인, 그래프 workflow, 원클릭 OpenTelemetry가 붙는다.

하네스 ① tool 호출 게이트 — Function middleware

모든 함수/도구 호출을 call_next() 앞뒤로 감싼다. 조건에 맞으면 MiddlewareTermination으로 체인을 끊고 실행을 차단한다.

from agent_framework import FunctionMiddleware, FunctionInvocationContext

class LoggingFunctionMiddleware(FunctionMiddleware):
    async def process(self, context: FunctionInvocationContext,
                      call_next):                       # call_next = 다음 단계(함수)
        print(f"[Function] Calling {context.function.name}")
        await call_next()                                # 진행
        print(f"[Function] {context.function.name} completed")

# 차단(short-circuit) 미들웨어
from agent_framework import AgentContext, AgentResponse, Message, MiddlewareTermination
async def blocking_middleware(context: AgentContext, call_next):
    last = context.messages[-1] if context.messages else None
    if last and last.text and "blocked" in last.text.lower():
        context.result = AgentResponse(
            messages=[Message(role="assistant", contents=["This request was blocked."])])
        raise MiddlewareTermination(result=context.result)   # 에이전트 실행 자체를 건너뜀
    await call_next()

.NET도 동일 패턴: agent.AsBuilder().Use(CustomFunctionCallingMiddleware).Build(), 시그니처는 ValueTask<object?> (AIAgent, FunctionInvocationContext, next, ct). context.Terminate = true로 함수-호출 루프 중단.

하네스 ② HITL 승인 — approval_mode

도구에 @tool(approval_mode="always_require")를 선언하면, 그 도구는 사람이 승인하기 전엔 실행되지 않고 run 결과에 user_input_requests(구조화된 일시정지 신호)가 담긴다. 호출 애플리케이션이 승인 authority가 되어 재제출한다.

from agent_framework import Agent, Message, tool
from agent_framework.openai import OpenAIChatClient

@tool(approval_mode="always_require")        # ← 선언적 승인 게이트
def get_weather_detail(location) -> str:
    return f"The weather in {location} is cloudy, humidity 88%."

async with Agent(client=OpenAIChatClient(), name="WeatherAgent",
                 instructions="You are a helpful weather assistant.",
                 tools=[get_weather_detail]) as agent:
    result = await agent.run("What is the detailed weather in Amsterdam?")
    # 실행 대신 승인 요청이 돌아온다
    for req in result.user_input_requests:
        if req.function_call:
            print("Approval needed:", req.function_call.name, req.function_call.arguments)
    # 승인 후 재제출 (True=승인)
    approval = Message(role="user",
                       contents=[req.to_function_approval_response(True)])
    final = await agent.run(["What is the detailed weather in Amsterdam?",
                             Message(role="assistant", contents=[req]), approval])
    print(final.text)

IFunctionInvocationFilterauto function loop 게이트플러그인C#·Python

📦 공개 저장소: microsoft/semantic-kernel

개요. Semantic Kernel의 function invocation filter는 "모든 함수/도구 호출을 가로채 인자 검사·단락(short-circuit)·결과 수정"하는 하네스 게이트의 정석이다. next 델리게이트를 호출하지 않으면 함수가 실행되지 않는다 — 즉 필터가 곧 통제면.

인터페이스 = 게이트 계약

// dotnet/src/.../Filters/Function/IFunctionInvocationFilter.cs
public interface IFunctionInvocationFilter
{
    // next 를 호출하지 않으면 함수/다음 필터는 실행되지 않는다
    Task OnFunctionInvocationAsync(
        FunctionInvocationContext context,
        Func<FunctionInvocationContext, Task> next);
}

// FunctionInvocationContext: 인자/결과를 읽고 바꿀 수 있다
public class FunctionInvocationContext {
    public KernelFunction Function { get; }
    public KernelArguments Arguments { get; }        // 검사·수정 가능

{
    public async Task OnFunctionInvocationAsync(
        FunctionInvocationContext context, Func<FunctionInvocationContext, Task> next)

            await next(context);                          // 재시도
        }
    }
}

export class RunInTerminalTool
  implements vscode.LanguageModelTool<IRunInTerminalParameters> {

  async prepareInvocation(options, _token) {
    // ← 여기가 하네스 게이트
    const confirmationMessages = {
      title: 'Run command in terminal',
      message: new vscode.MarkdownString(
        `Run this command in a terminal?\n\n\`\`\`\n${options.input.command}\n\`\`\`\n`),
    };
    return { invocationMessage: 'Running command in terminal', confirmationMessages };
  }

  async invoke(options, _token) {            // 승인된 뒤에만 실행
    const term = vscode.window.createTerminal('Language Model Tool User');
    const exec = term.shellIntegration!.executeCommand(options.input.command);
    let out = ''; for await (const c of exec.read()) out += c;
    return new vscode.LanguageModelToolResult([new vscode.LanguageModelTextPart(out)]);
  }
}

하네스 ① 권한 게이트 — Review 모드 · OBO · RBAC

에이전트마다 user-assigned managed identity가 붙고, 기본은 Reader(읽기). 쓰기가 필요하면 OBO(On-Behalf-Of) 승인 프롬프트가 떠서 사람 자격증명으로 단일 실행(캐시 안 함)한다. Review 모드=모든 쓰기 승인, Autonomous 모드=관리 ID 직접 실행.

하네스 ② 검증 게이트 — Agent Hooks (Stop / PostToolUse)

라이프사이클 지점에 prompt형(LLM 판정) 또는 command형(샌드박스 스크립트) 훅을 걸어 완결성 검증·위험명령 차단·감사를 한다. Claude Code hooks와 판박이 구조를 관리형으로 제공.

api_version: azuresre.ai/v2
kind: ExtendedAgent
metadata: { name: my_hooked_agent }
spec:
  instructions: |
    You are a helpful assistant.
  hooks:
    Stop:
      - type: prompt
        prompt: |
          Check if the response ends with "Task complete." $ARGUMENTS
          Respond {"ok": true} or {"ok": false, "reason": "..."}.
        timeout: 30
    PostToolUse:
      - type: command
        matcher: "Bash|ExecuteShellCommand"
        failMode: block
        script: |
          #!/usr/bin/env python3
          import sys, json, re
          ctx = json.load(sys.stdin)
          cmd = ctx.get('tool_input', {}).get('command', '')
          for p in [r'\brm\s+-rf\b', r'\bsudo\b', r'\bchmod\s+777\b']:
              if re.search(p, cmd):
                  print(json.dumps({"decision": "block", "reason": f"Blocked: {p}"})); sys.exit(0)
          print(json.dumps({"decision": "allow"}))

하네스 ③ 실행 격리 + ④ 관측

  • 4-요소 샌드박스: reasoning(본체) / tool 실행(에이전트당 micro-VM ADC 샌드박스) / identity sidecar(자격증명 격리) / network proxy(모든 아웃바운드 검증). tool 프로세스는 호출마다 새로 뜨고 끝나면 프로세스 트리 전체 종료 — "한 tool 호출이 다른 호출의 환경을 못 본다".
  • secretless: identity sidecar가 tool process별 short-lived token을 발급하고, action token은 tool call별 single-use다. 자격증명은 reasoning 컨텍스트에 들어가지 않는다.
  • 관측: 생성 시 Application Insights·Log Analytics 자동 생성. trace/span ID 상관, 모든 아웃바운드 호출의 method·URL·duration·status, 훅 활성화 이벤트까지 고객 소유 App Insights로.

팀 하네스 맥락 · 결과 · 에피소드

  • 맥락: 인프라 인시던트 대응·운영·RCA의 agentic Ops. 핵심 원칙: "에이전트가 변경을 제안하면 팀이 승인 — 사람 사인 없이는 배포 없음." reasoning runtime, tool-execution micro-VM, identity sidecar, network proxy를 분리하고, action token은 tool call별 single-use로 발급한다.
  • 결과: Review 모드(모든 쓰기 승인) vs Autonomous 모드. 훅(azuresre.ai/v2·ExtendedAgent)으로 완결성 검증·위험명령 차단. 생성 시 App Insights·Log Analytics 자동 생성.
  • 에피소드: "controlled autonomy" — 팀은 raw 알림이 아니라 "왜 이 신호들이 묶였는지" 요약된 이슈로 일하고, 에이전트는 리소스 재시작·설정 변경을 스스로 하지 않는다(triage·조사까지만).

💰 토큰 절약 포인트: 알림을 이슈(issue)로 상관(correlation)해 토큰을 아낀다 — 자율 운영 모드가 서로 연관된 여러 알림을 하나의 이슈로 묶으므로, 알림마다 근본원인 분석을 따로 돌리는 대신 한 번만 조사한다(중복 조사에 드는 컨텍스트·토큰 제거). 또 세션 insights·memories에 이전 조사 결과와 운영 토폴로지를 축적·재사용해, 다음 인시던트에서 같은 배경을 처음부터 다시 수집하지 않는다. 커스텀 인스트럭션으로 "이 두 시스템은 상관없다" 같은 도메인 지식을 미리 주입하면 잘못된 상관을 좇는 조사 토큰까지 예방한다. (도구 호출마다 새로 뜨는 process와 호출별 자격증명은 본래 보안 격리용이지만, 호출 간 환경이 섞이지 않게 하는 부수 효과도 있다.)

@tool(approval_mode="never_require")   # 도구별 승인 정책(하네스 제어 파라미터)

관통하는 6가지 인사이트

  1. 하네스 = 파일로 코드화된다. 16개 중 대다수가 리포 안의 텍스트 파일(AGENTS.md·CLAUDE.md·SKILL.md·*.yml·settings.json)로 통제를 표현한다. "적혀 있지 않으면 존재하지 않는다."
  2. 검증 게이트가 품질을 만든다. SWE-agent의 edit-lint 자동 롤백, Aider의 reflection loop, Claude/Codex의 Pre/PostToolUse — "느낌"이 아니라 린트·테스트·정책의 exit code로 판정한다. 이 층이 없으면 빨라져도 반복 가능하다 말할 수 없다.
  3. 권한은 늦게 연다. read-only·workspace-write에서 출발해 쓰기/배포/외부 action을 마지막에 승격. MCP 도구는 "자율 사용 + 승인 없음"이 기본이므로 읽기 전용만 허용목록.
  4. 격리가 자율성을 가능하게 한다. ephemeral Actions 러너·Docker·git worktree가 있어야 에이전트에게 큰 자율을 줘도 안전하다.
  5. 학습 환류가 "복리(compound)"를 만든다. Compound Engineering의 /ce-compound가 극단적 예 — 에이전트가 자기 지침(CLAUDE.md)을 갱신. Anthropic의 self-improving 툴 설명도 같은 원리.
  6. 멀티에이전트는 만능이 아니다. 탐색·리서치엔 병렬(Anthropic)이, 결정이 얽힌 구현엔 단일스레드+컨텍스트 공유(Cognition)가 유리. 컨텍스트 무결성 > 병렬성이 기본값.
  7. Microsoft는 통제면을 프레임워크 1급 시민으로 만든다. MAF의 middleware 체인·approval_mode, SK의 invocation filter, VS Code의 prepareInvocation, SRE Agent의 permission gate·hooks·micro-VM 샌드박스, Foundry의 guardrails·OTel — 모두 "에이전트 코드"가 아니라 인터셉트·승인·격리·관측 지점을 API로 노출한다. 앞의 오픈소스 사례(SWE-agent lint 게이트, Claude hooks)와 같은 원리를 관리형·프로덕션급으로 제공.
