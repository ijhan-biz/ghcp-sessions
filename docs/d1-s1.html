토큰 최적화 & 가드레일 — 적게 주고 더 정확하게

전체 레포를 던지는 습관을 버리고 범위를 좁혀 같은 결과를 더 적은 토큰으로 얻는 법을 익힙니다. 동시에 가드레일을 프롬프트에 명시하고, 이후 모든 실습에 쓸 본인 기능 스펙을 비식별화합니다.

PT-01 토큰 최적화PT-09 범위 축소PT-06 #filePT-03 가드레일OR-14 비식별화HE-12 Cost burn

학습 목표

  • 토큰이 어디서 새는지(과다 컨텍스트·반복 첨부·긴 로그) 이해하고, 파일 범위·#file·로그 제한으로 줄인다.
  • 제약을 가드레일로 프롬프트에 명시한다(외부 패키지 금지·시그니처 유지·민감정보 출력 금지).
  • 본인 기능 스펙 1건을 비식별화해 이후 세션의 공용 재료로 만든다.

미니강의 — 컨텍스트는 비용이자 정확도다

Copilot은 한 번에 처리할 수 있는 컨텍스트 윈도우(PT-12)가 정해져 있습니다. 불필요한 파일을 잔뜩 넣으면 ① 비용이 오르고(HE-12 cost burn), ② 정작 중요한 코드가 묻혀 정확도가 떨어집니다. 좋은 컨텍스트 관리(PT-02)는 비용과 품질을 동시에 잡습니다.

범위 축소 3종 (PT-09)

FILE.SCOPE

#file:path/to/file로 특정 파일만 지정(PT-06). "이 레포 전체" 대신 "이 함수만".

LOG.TRIM

에러 로그는 전체가 아니라 관련 30~80줄만. 스택트레이스 핵심만 붙입니다.

OUTPUT.LIMIT

출력 형식·길이를 지정해 장황한 응답을 막습니다(PT-10).

가드레일 = 하네스의 출발점 (PT-03)

"외부 패키지 추가 금지", "public API 시그니처 유지" 같은 자연어 제약이 가드레일입니다. Day2에서 이 문장들을 실행 가능한 검증으로 바꿉니다(HE-01 하네스 엔지니어링). 오늘은 프롬프트에 명시하는 습관부터 만듭니다.

실습 1 — 토큰 절약 Before/After

샘플(EN-13 aibuild-kpx 등)에서 같은 작업을 두 방식으로 시키고 결과·토큰 감각을 비교합니다.

Before · 과다 컨텍스트
"이 레포 전체를 보고 결제 로직 버그를 고쳐줘" + (전체 폴더 첨부)

문제: 범위 과다 · 금지 작업 없음 · 완료 기준 없음 · 민감정보 경계 없음.

After · 범위 한정 + 가드레일
[맥락] 기능 스펙(비식별): 음수 금액은 오류, 면세 품목 VAT 0%, 일반 VAT 10%.
[작업] #file:src/billing/tax.ts 의 calcVat() 만 검토. 음수 입력 가드 누락 의심.
[제약] 기존 시그니처 유지, 외부 패키지 추가 금지, 유닛테스트 포함.
[출력] 변경 요약 → 코드 → 테스트 순서로.
관찰 포인트: After가 더 짧은 입력으로 더 정확한 변경을 낸다는 점, 그리고 가드레일 덕분에 "엉뚱한 파일까지 고치는" 일이 사라진다는 점을 직접 확인합니다.

실습 2 — 본인 기능 스펙 비식별화

Day2까지 이어갈 얇은 end-to-end 기능 1건을 정하고 비식별화합니다(OR-14). 1~2개 파일에서 구현 가능하고, 테스트로 확인 가능하며, 운영 배포·실제 결제·DB 마이그레이션이 필요 없는 기능을 고릅니다.

체크포인트 & 산출물

산출물: ① 범위를 좁힌 토큰 절약 프롬프트 1개 이상, ② 가드레일이 명시된 프롬프트, ③ 비식별 기능 스펙 카드(이후 모든 세션의 재료).
  • 전체 레포가 아니라 파일/함수로 범위가 좁혀졌는가?
  • 금지 작업·민감정보 경계가 프롬프트에 들어갔는가?
  • 기능 스펙 카드에 고객 식별자·secret·실제 로그가 없는가?
컷라인: 토큰 정량 측정이 어려우면 "입력 길이 대비 결과 품질"의 체감 비교만으로 충분합니다.

흔한 실수 & 공유 포인트

  • 가드레일을 머릿속에만 두고 프롬프트에 안 씀 → 모델은 안 적은 제약을 모릅니다.
  • 비식별화한다고 로직까지 바꿈 → 로직은 유지하고 특정 대상만 일반화합니다.
공유 포인트: "어떤 범위 축소가 가장 효과적이었나"를 한 줄로. 토큰 절감은 팀 비용에 직접 닿는 주제라 공유 가치가 큽니다.
