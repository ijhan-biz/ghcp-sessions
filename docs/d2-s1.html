하네스 엔지니어링의 개념(자연어 제약 → 실행 가능한 검증)을 세우고, VS Code Agent 모드를 그냥 실행하지 않고 도구 권한을 좁히고 로그를 남기는 습관을 만듭니다. 도구 승인·denyList·도구 호출 내역을 다루고, 그 기록을 해석하는 법까지 익힙니다.

미니강의 — 프롬프트 약속을 실행 밖으로 옮긴다

Day1에서 가드레일을 프롬프트에 적었습니다. 하지만 프롬프트 안의 약속은 모델이 어길 수 있습니다. 하네스는 그 약속을 실행 경로 바깥의 결정론적 검사(HE-06)로 옮깁니다. 오늘(S1)은 그 첫 단계로 Agent 모드의 도구 권한과 로그를 다룹니다.

주의: VS Code Agent 모드의 도구·터미널 자동승인 설정 키는 버전에 따라 다를 수 있습니다. 실습 시작 시 현재 VS Code 버전의 설정 화면(검색: "auto approve", "terminal")을 기준으로 삼습니다. Agent 모드가 안 되면 Copilot Chat(CF-01)으로 관찰하고 강사 데모 로그를 분석합니다.

VS Code 기반 — Agent 모드에서 같은 하네스

참가자 대부분은 VS Code Copilot을 씁니다. 하네스의 핵심(권한 최소화·로그·차단)은 Agent 모드에서 만듭니다. Chat 모드 선택기의 Ask · Edit · Agent 중 Agent가 도구를 실제로 실행하는 경로입니다.

하네스 요소 ↔ VS Code Copilot Agent 방법

왜 로컬 게이트가 필요한가: 모델·UI 승인만으로는 100% 막지 못합니다. 그래서 "실행 경계 밖"의 policy-check(D2·S2)가 최종 안전장치입니다.
설정 키 주의: VS Code의 도구·터미널 자동승인 설정 키는 버전에 따라 다릅니다(설정 검색에서 "auto approve", "terminal" 등). 현재 VS Code 버전의 설정 화면을 기준으로 삼으세요.

실습 — 권한을 좁힌 Agent 실행

STEP 1 · Agent 모드 준비

Chat 모드 선택기를 Agent로 두고 워크스페이스를 신뢰(Trust)로 엽니다. 설정에서 터미널 자동승인(allow/deny)과 도구 승인 동작을 확인합니다.

STEP 2 · 권한을 좁힌 요청

Agent에게 "현재 브랜치 변경 파일과 테스트 명령 후보를 요약"을 요청하고, 도구 실행 승인에서 git 읽기만 허용하며 rm·force 같은 위험 명령은 거부(denyList)합니다. .github/copilot-instructions.md에 금지 작업을 명시해 두면 매번 반복하지 않습니다.

STEP 3 · 도구 호출 내역/로그 해석
[작업] 아래 Agent 도구 호출 내역(또는 세션 로그 events.jsonl)을 보고 요약해라.
[출력] 실행 의도 · 사용 도구 · 차단된 작업 · 다음에 필요한 권한 · 위험 신호.

체크포인트 & 산출물

산출물: 도구 승인·denyList가 적용된 Agent 도구 호출 내역(또는 세션 로그) + 해석 메모.
  • 도구 승인에서 허용 도구가 좁혀졌는가(git 읽기 등)?
  • denyList로 위험 명령(rm·force)이 명시적으로 막혔는가?
  • 로그에서 "무엇을 했고 왜 멈췄는가"를 한 문장으로 말할 수 있는가?
컷라인: 개념(권한 최소화·로깅)만 잡으면 통과입니다. Agent 모드가 어려운 환경은 강사 데모의 도구 호출 내역/로그 분석으로 대체합니다.

참조 심화 — 차단 패턴 · logging-first

차단 권장 명령 패턴

rm -rf · git push --force · kubectl delete · terraform apply · git rebase -i — 위험도에 따라 warn 또는 block.

핵심 원칙: "프롬프트만으로는 안전하지 않다 — 정책은 실행 경계에 붙인다." 실행 전(pre-check)과 후(post-check)를 모두 검사하고, 처음 1~2주는 log-only로 오탐을 관찰한 뒤 차단으로 승격합니다(logging-first).

흔한 실수 & 공유 포인트

  • 권한 제한 없이 Agent 실행 → 에이전트가 무엇이든 할 수 있는 상태. 항상 도구 승인·denyList로 좁힙니다.
  • 프롬프트에 모델명을 적고 "그 모델로 돈다"고 가정 → 보장되지 않습니다(CF-10, S2에서 자세히).
공유 포인트: "deny-tool로 막은 위험 명령" 사례. 팀 보안 관점에서 바로 쓸 수 있는 공유 거리입니다.

이 세션의 실행 코드 (Hands-on)

권한을 좁힌 Agent 실행 + 결정론적 게이트 확인:
# (새 창) sample-project-activity-log — VS Code Agent 모드에서
#  1) Agent에게 "변경 파일과 테스트 후보 요약" 요청 → 도구 승인에서 git 읽기만 허용, rm·force 거부
#  2) 도구 호출 내역/세션 로그로 "무엇을 했고 왜 멈췄는가" 확인
npm run policy-check   # 승인과 무관하게 실행 경계 밖에서 위험 변경을 최종 차단(S2로 연결)
